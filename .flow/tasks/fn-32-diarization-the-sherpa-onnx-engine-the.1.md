# fn-32: Diarization, the sherpa-onnx engine, the post-meeting speaker pass and speaker names

**R1 (the engine).** `dettivo-engine-diarize` is the fourth engine process: `crates/sherpa-onnx-sys` fetches the pinned sherpa-onnx 1.12.9 Linux release archive at build time (SHA-256 in `build.rs`; `SHERPA_ONNX_ARCHIVE_DIR` and `SHERPA_ONNX_DIST_DIR` for offline builds), keeps `libsherpa-onnx-c-api.so` and its `libonnxruntime.so`, and binds the offline speaker diarization C API with bindgen; the engine links it dynamically with an `$ORIGIN`-based run path so ONNX Runtime lives in that one process. `dettivo-engine-proto::host_diarize` is the streaming host (a pass on its own thread, `status` busy meanwhile, `cancel` answered at once with the result dropped, later requests queued), `load` gains `threads`, `diarize` gains `clustering_threshold`, and `progress` gains `completed` and `total` with fixtures `request.load.threads.json` and `event.progress.chunks.json`. CLI mode `--wav --model --json [--speakers n]` prints the protocol's `turns`. Verified by `crates/dettivo-engine-diarize/tests/{cli,protocol}.rs` (the two-speaker fixture lands six turns of two speakers within 250 ms of the expected starts; a missing model is `model_missing` naming the path; a bad WAV is `bad_request`; load, diarize with chunk progress, cancel, status busy, unload over the protocol), the host's unit tests, and `dettivo-qa pipeline diarization --bench`: DER 0.020 (missed 0.011, false alarm 0.009, confusion 0.000) with exactly two speakers, 16.5x realtime on four CPU threads (NFR-4 asks for 4x). CI fetches the model set with `scripts/models/fetch-diarization-model.sh` and runs the fixture tests and the pipeline on the CPU.

**R2 (the post-pass).** `crates/dettivo-meeting/src/diarize.rs` reads every take of the diarized track onto the meeting clock with silent gaps (an import's single file too), renumbers the engine's labels by first appearance, and assigns under the rule: coverage ≥ `min_coverage` (0.25) and the winner's share ≥ `min_speaker_share` (0.60), else unlabelled; microphone segments are `You`; a room-audio meeting assigns every segment. `crates/dettivod/src/diarization.rs` runs the job when a finalisation or a meeting import lands `completed` under `auto` (the meeting's own `diarize` first) or on `meetings.diarize`, publishes `job.progress` with `stage = diarizing` and `meeting.state` with `diarization_status`, stores the speakers (`talk_ms`, `color_index`) and the diarization block, and records `unavailable` with the download command when the model set is missing while the meeting stays `completed`. Verified by the unit tests in `diarize.rs` (the straddling segment and the silence-heavy one stay unlabelled, room audio, name carry-over) and `crates/dettivod/tests/meetings_diarize.rs` (a two-track mock meeting with the fixture as the system track: `You` on microphone segments, remote labels consistent with the expected turns, three speakers with talk time, `job_diarize_1` progress under `diarizing`; a microphone-only import diarizes the whole track with no `you`; a tree without the model set leaves `unavailable` with the command and the transcript intact).

**R3 (re-run).** `meetings.diarize { meeting_id, speakers? }` replaces the assignment with fresh progress, keeps names by id when the diarized count matches, and answers `CONFLICT` `diarizationRunning` while a pass runs, `meetingNotCompleted` before finalisation, `diarizationDisabled` under `enabled = false`, and `NOT_FOUND` `modelMissing` naming the download command. `meetings.cancel` on a completed meeting stops a running pass. Verified in `meetings_diarize.rs` (job_diarize_2 after a rename keeps "Amy" through the re-run; the running conflict; the not-completed conflict on a recording meeting; the model-missing fixture replay).

**R4 (crash isolation).** `crates/dettivod/tests/meetings_diarize_crash.rs` links the supervisor's scripted `fake-engine` as `dettivo-engine-diarize` (the fake engine gained `diarize` and a `crash-on-diarize` marker): the first pass dies mid-request and the row records `failed` with the engine's last redacted stderr line, `system.ping` answers, the meeting stays `completed` with its transcript; two more passes die on load and the third crash in a row marks the engine degraded on `engine.state` and `speech.engines` (crashes 3); after the backoff a fourth pass lands `ready` and the row is whole again. `speech.engines` and `dettivo doctor` gain the diarize row (with the model set's readiness in doctor's `diarize` line).

**R5 (names, fixtures, the model set).** Migration `0005-speakers` adds `meeting_speakers`, `speaker_names`, the `diarization` JSON column and a `speaker_names` column joined to the meetings FTS index. `meetings.speakers.rename` updates the speaker and every segment's `speaker` text (`txt`, `md` lines, `srt`/`vtt` cues, `json` speakers) and remembers the name; `meetings.speakers.suggest` orders by recency; an over-long name is `INVALID_PARAMS` naming the 64-character limit. The catalogue learns multi-file model sets with a `tar.bz2` unpack step (`diarize/diarization`: pyannote segmentation 3.0, MIT, and 3D-Speaker ERes2Net, Apache-2.0, 47 MB); the downloader fetches the files under one progress, verifies each and the unpacked member, and one mismatch quarantines the set; `speech.models.*` accept `provider = "diarize"` while the selection methods hide it. Verified by `meetings_diarize.rs` (rename reaches every export format, `meetings.search` finds "lovelace", suggest lists it first, empty name restores `Speaker 1`; the `speakers.list`, `speakers.rename`, `speakers.suggest`, both rename error fixtures and `diarize.json` replay against the seed and the live daemon), the store's multi-file readiness/verify/quarantine/delete unit test, the catalogue test, and `cargo run -q -p dettivo-qa -- contract` (81 passed, 0 failed, the stateful speaker fixtures recorded in both stateful lists).

**R6 (docs and config).** `docs/meetings.md` gains the Speakers section (the rule, the labels, the re-run, the names, the CLI), `docs/engines.md` the fourth engine (binary, CLI example, the Diarization section, the protocol additions, the doctor rows), `docs/models.md` the model set and multi-file catalogue entries, `docs/qa.md` the pipeline, `docs/api/linux-deltas.md` the four methods and every field addition, `docs/config.md` the `[meetings.diarization]` table and `[engines.diarize] threads`; `config print-default` prints both sections (schema, `DEFAULT_TOML`, the print_default fixture). ADR 0035 records the in-repo binding over `sherpa-rs`, the engine, the model set, the assignment rule and the bounds, indexed in `docs/adr/README.md`. CLI: `dettivo meetings diarize <id> [--speakers n]`, `dettivo meetings speakers <id>`, `dettivo meetings speakers rename <id> <speaker-id> <name>`, `dettivo meetings speakers suggest`, `dettivo speech download --provider diarize --model diarization`.

### Left out on purpose

No GUI (the speaker popover, talk-time bar and swatches are S-27; `color_index` is their slot), no live diarization, no GPU path (T6), no notes, analysis or delete-policy changes (S-26, fn-33). `meetings.delete` is untouched (fn-33 owns it): a meeting deleted while a pass runs has its result dropped when the pass ends, and `meetings.cancel` on the completed meeting stops the pass. The engine's `cancel` answers at once but sherpa-onnx cannot stop mid-pass, so the process stays busy until the pass returns (the supervisor's reaper ends an idle one). The supervisor's degrade rule is unchanged: three crashes in a row without a successful load between them, which the crash test exercises with a request crash followed by two load crashes.
