## Done summary
Settings is now the config file with a face. The eight sections under `qt/qml/Dettivo/app/settings/` are editors over `config.toml` through the daemon's `config.*` methods: every row shows the key's name and the sentence the default file documents it with, writes the moment a value is committed, shows the daemon's refusal under the control when a value does not fit, follows the file after a hand edit or a CLI write through the `config.changed` event, and every section ends with the TOML it writes while the column keeps the file one click away. The host side (`SettingsModel`, `ModelsTable`, `HotkeysSetupModel`, `AgentsModel`, `DoctorModel`, the `settings_keys.cpp` table) came from the previous worker's two commits; this session made the tree compile and render, fixed the pattern's layout and bindings, and worked every acceptance criterion to done.

R1 is met by `settings_roundtrip` (`crates/dettivo-qa/src/scenarios/settings_roundtrip.rs`, `settings_checks.rs`, `settings_support.rs`), which opens every section over the profile's daemon and edits every key through its own control: fields are typed into, switches clicked, segments and combo boxes picked, each row scrolled into view through the new `dettivo app open settings.<section> --id <key>` deep link. Each key reads back through `config.get` with source `file` and is restored with `config.unset`; the comment planted in the profile's file survives every write; an invalid value shows the daemon's refusal under the field with the file untouched. The evidence (`roundtrip.json`) records 86 keys written or refused inline through their controls, `ipc.socket` locked by `DETTIVO_IPC_SOCKET`, and two keys left to the file with the reason (`ipc.auth_mode`, because `peer_token` would lock the drive out of its own daemon; `speech.provider`, written by the model choice together with the model). `scripts/lint-settings-keys.sh` holds the `config.keys` fixture, the app's key table and docs/config.md's "Keys by route" together and joins `make lint`; it fails by name on an undeclared key and passes on the branch (89 schema keys, 86 edited, 3 with a reason). The drive is registered in CI on both drivers under Xvfb.

Two product defects surfaced on the way and were fixed at the root. The daemon read, changed and wrote `config.toml` without a lock, so a `config.set` from the app and a `config.unset` from another connection could interleave and bring a removed key back; every writer (`config.set`, `config.unset`, `speech.selection.set`, `llm.endpoints.trust`, the Polish rule and app writes) now goes through one `edit_file` under the daemon's edit lock. The field also committed the same text twice (on Enter and again when the focus left); it commits once now, and a click selects the whole text once its release is done so typing replaces the value.

R2 is met by the visual manifest's `settings` surface, which cuts Models, Hotkeys and Agents into two regions each of their artboards right of the section column (the selections and the table, the bindings and the snippet with its panel, the fact panels and the host table) and holds them on Black Gold at both scales (0.57 to 0.84), with approved renders on the other four themes; `settings-pattern` renders General whole as an approved render on every theme for the five sections that follow the pattern. `dettivo-qa visual` passes 70 of 70 entries for the two surfaces and the canary fails every one of them as it should. Matching the artboards took three layout changes: the model table's detail wraps onto a second line the way the artboard's rows do, the selection boxes take the artboard's widths, and Hotkeys keeps a binding row's worth of air before the snippet where the artboard draws a fifth, non-config `Open Dettivo` row.

R3 is met on every section: the "This route writes" block renders the keys as TOML with the values in force, one line per table; the column's `open in editor` hands the file to `xdg-open` through `QDesktopServices` (the drive proves it with a stubbed `xdg-open` that records the path); a key the environment sets shows the `env · VARIABLE` chip and its control is disabled (the drive asserts the chip on `ipc.socket`).

R4 is met: the Agents route renders the socket and REST facts, the four MCP hosts with the file each reads and whether Dettivo's entry is in it, and `Write config` runs `dettivo mcp config --host <id> --write`, the one code path that writes host files (the drive sees `~/.mcp.json` gain the entry and the row turn `configured`); the app runs the command line from home so a project-scoped host file lands there. Diagnostics runs `dettivo doctor`, shows the report line by line with the exit code as the verdict, and copies it (the drive reads 37 report lines and clicks `Copy report`). The Agents column reads `Agents`, `Overview`, `MCP hosts`, `REST shim`, `CLI` as agents.png shows, and a click scrolls to the block.

R5 was largely in place from the previous worker's first commit (`config.keys` and `config.changed` with fixtures, the delta register rows, `dettivo config keys --json` over the daemon's registry, `crates/dettivod/tests/config_live.rs`); this session proved the refresh end to end: the drive edits the file by hand while Hotkeys is open, and the `hotkeys.hold` field shows `F7` with the notice `The file changed on disk; 1 value(s) refreshed.` under the title. The platform test now counts the seven config methods `config.keys` made, which the previous commit had left failing.

R6 is met by ADR 0033 (`docs/adr/0033-settings-routes-config-editor-key-registry.md`, indexed), the Settings section of docs/app.md with the `--id <key>` deep link and the per-section table, the "Keys by route" section of docs/config.md that places every key on its route and names the three that stay in the file (lint-checked), the drive and the two visual surfaces in docs/qa.md, the implemented artboards and the surfaces table in docs/design/README.md, the approvals in docs/design/baselines.md, and the settings names in docs/qa/a11y-names.md.

Verification: `flock /tmp/dtv-gate.lock make build test lint` is green at the final commit (51 Qt tests, the workspace's Rust tests, clippy, the file-length, edge, delta, QML, token, icon, accessible-name and settings-key lints, the docs check and rustdoc); `cargo run -q -p dettivo-qa -- contract` reports 71 passed, 0 failed; `cargo run -q -p dettivo-qa -- visual --surface settings` and `--surface settings-pattern` pass every entry and the canary fails every entry; `settings_roundtrip` passed on the in-repo driver on the live desktop through a private accessibility bus (Xvfb is not installed on this machine, so the CI job under `scripts/qa/xvfb-session.sh` is where both drivers run it unattended; the cua driver was not run here).

Deliberately left out: an `Unload` action on a warm model (no daemon method unloads an engine on demand); the artboard's fifth binding row (`Open Dettivo` has no key in the schema) and its two backend toggles (the schema has one `hotkeys.backend` choice); a Polish rule and app-profile editor in the app (`polish.rules`, `polish.apps` and `polish.presets` are tables of tables edited through `dettivo polish` and the file, recorded as excluded with the reason and named under "Keys by route"); a REST port and token editor (the REST shim's keys arrive with the REST spec, the panel says so).
