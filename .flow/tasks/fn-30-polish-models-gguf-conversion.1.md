## Done summary
# fn-30: polish models, GGUF conversion, the sideloaded fine-tune, the eval harness port and the hard-gate report

R1, the sideload. `[llm] polish_experiment` names a manifest under `[llm] experiments_dir` (`<models>/polish-experiments` by default) in the macOS shape (`id`, `displayName`, `relativeModelPath`) with the two Linux additions `format` (`gguf` or `gguf-lora`) and `baseModel`. `dettivo_speech::llm::sideload::resolve` turns it into the one GGUF its directory holds and names every failure (missing manifest, not a manifest, a path outside the directory, no or two GGUFs, an adapter without a base); it is unit-tested against the macOS shape and both Linux forms. The daemon's `LocalLlm` binds the result, a fused GGUF in place of the catalogue file or an adapter over its base through the engine protocol's new `load.lora` (the LLM engine initialises the adapter once and sets it on every context, the supervisor reloads when the adapter changes, the CLI mode takes `--lora`). `llm.models.status` lists the sideload as a row with `source = "sideload"`, `format`, `base_model`, the selection mark and `manifest_error`, its result carries `polish_experiment`, `llm.engine.status` carries `lora`, and the catalogue methods answer `NOT_FOUND` naming the catalogue ids for a sideload id. `dettivo llm experiment status|use|clear` and a `dettivo doctor` line are the surfaces. Verified by `crates/dettivod/tests/llm_sideload.rs` against a live daemon: the fused row, the adapter over a missing base naming the base and its download command, an unresolvable manifest reported by name with the provider back on `[llm] model`, and, with the Qwen3 1.7B file on this machine standing in for the tune, a `polish.test` in `enhanced` mode that names the sideload as its model.

R2, the harness. `dettivo-qa polish-eval` (`crates/dettivo-qa/src/polish_eval/`) reads the macOS canonical JSONL (with the spec's `expected`, `bundle_id`, `protected_tokens` as aliases), starts a daemon in an isolated profile with `[llm] provider = "local"` and the candidate (a catalogue id hard-linked into the profile, `sideload[:<name>]`, a GGUF path, or `fixture:<dir>`/`echo`), runs every row through `polish.test` in `enhanced` mode, scores it with `score_results.py` ported case for case, gates it with `check_promotion.py` ported against `qa/polish-eval/targets.json` (the macOS promotion targets) plus the Linux rule that relative gates compare only reports from one backend, and writes the report. Verified by unit tests with one passing and one failing row per macOS metric, the Python percentile and median, the gate's three outcomes, and by `crates/dettivo-qa/tests/polish_eval.rs`, which runs the twelve synthetic rows of `fixtures/polish-eval/sample.jsonl` with the recorded rewrites through a real daemon and compares with `golden.json` (a differing metric fails naming it), checks an unknown preset fails naming the row, and scans the checked-in reports for row text. `just qa-polish-eval` runs the same in CI's drive job.

R3, the reports. On this machine (RTX 4090, the Vulkan engine build) both private held-out sets ran through `qwen3-4b-instruct-2507` and through a 1.7B sideload converted by the runbook from the public Qwen3-1.7B checkpoint and installed as `current` (the private fused export lives on the macOS machine and is one copy plus the same script away). The four reports and the regenerated README are under `docs/reports/polish-eval/`, every hard gate stated per metric, the relative gates against the 4B incumbent (the 1.7B improves median and p95 with no quality regression), the raw-generation figure (`--engine-only`: 87-102 tokens/s for the 4B, 162-163 for the 1.7B) and the comparison with `macos-baseline.json`. Both models fail the quality gates on both sets for one reason the row outputs make plain: the daemon's raw layer treats a full stop inside a token as a sentence end (`index.ts` reaches the model as `index. Ts`), so protected tokens with dots are gone before any model sees them and the guard rejects the rewrite; that is a raw-layer defect outside this spec's boundary and the reports make it visible. The reports carry metrics, row ids, the model file and its SHA-256, the backend, the engine version and the git sha; the test scans them for text.

R4, the dictionary eval. `crates/dettivo-language/tests/dictionary_eval.rs` scores the twenty public rows of the macOS `eval-v1.jsonl` (checked in as a golden with each row's macOS `exact`-strategy output) through `dettivo_language::raw` with the dictionary as whole-word replacements and holds every figure and row outcome to `docs/reports/polish-eval/dictionary-eval-v1.json`. The report records a gap, not parity: Linux has no dictionary corrector, whole-word replacement scores 0.2 exact match against the macOS `exact` strategy's 0.4 and the shipped `hybrid` strategy's 1.0, and it over-applies to common words and inside URLs (4 false positives); the rows that differ are listed by name. Reaching the macOS figure means porting the corrector, a spec of its own.

R5, the conversion. `scripts/models/convert-polish-finetune.sh` pins llama.cpp at the revision `llama-cpp-2 0.1.156` vendors (`e79e4bf6…`), converts a fused export with `convert_hf_to_gguf.py` to F16 and quantises with `llama-quantize` to Q4_K_M, or a PEFT adapter with `convert_lora_to_gguf.py`, writes the SHA-256 and the manifest, names every step and stops on the first non-zero exit naming it, and with `--verify` loads the result in `dettivo-engine-llm --prompt`. `--dry-run` validates the toolchain and the paths; CI runs it against `scripts/models/fixtures/hf-checkpoint` (`just polish-convert-check`, `python` added to the CI toolchain). On this machine the full run converted Qwen/Qwen3-1.7B into a 1.3 GB Q4_K_M GGUF the engine loaded in CLI mode and the daemon then ran the held-out sets on.

R6, the docs. `docs/polish-models.md` (the runbook, the manifest, the opt-in key, the eval command, how to read a report), `docs/config.md` (both keys), `docs/engines.md` (`lora`), `docs/api/linux-deltas.md` (the new fields, the fixture updated), `docs/qa.md`, `docs/polish.md`, `docs/models.md`, and ADR 0027 recording the sideload path, the harness port and the optional-first rule; `just docs` passes.

Deliberately left out: no fine-tuning on Linux; no catalogue entry or download for a fine-tune; no change to the polish layers, the raw layer or the goldens (the raw-layer sentence-end defect and the missing dictionary corrector are recorded, not fixed); `--dictionary` on `dettivo-qa` was not added because `dettivo-qa` may not link `dettivo-language`, so the dictionary eval lives with the layer as a test; a real LoRA adapter was not converted (no PEFT export on this machine) and the adapter path is proven at the resolver, engine and daemon level with placeholders.

Verification: `make build`, `make test-rust` (97 test binaries green; run without `DETTIVO_QA_MODE` in the environment, which the daemon's own `qa_env` test refuses), `make test-qt` (48 of 48) and `make lint` (fmt, clippy, edges, file length, deltas, QML lints, docs, rustdoc) all exit 0 at 95fea1a; `dettivo-qa contract` replays 66 fixtures passed, 0 failed, 25 skipped as stateful, 19 pending, and the MCP harness 42 passed. The Vulkan runs used an engine built with `--features vulkan` under the ignored `target/vulkan` (the workspace build overwrites `target/debug/dettivo-engine-llm` with the CPU build, which is why `polish-eval --engines-dir` exists). Leftovers outside the repository, deletable: `~/.cache/dettivo/fn30-venv` (941 MB, the conversion interpreter; the /tmp copy was removed), `~/.cache/dettivo/fn30-experiments` (the converted 1.7B sideload), `~/.cache/dettivo/fn30-target-vulkan` (a failed build attempt), the llama.cpp checkout and the Qwen3-1.7B download in the scratchpad and the Hugging Face cache.
