# The app

`dettivo-app` shows what Dettivo is doing: whether it is ready, where the next take lands, the mode and input, today's dictations, and the engines and agent surfaces. It follows the Omarchy theme without a restart and opens Home without initializing audio playback. Session and model facts come from the daemon over the same socket the command line uses ([docs/daemon.md](daemon.md)); the host model reads local agent configuration files. The approved design is `docs/design/studio/baselines/home.png`; the decisions behind the host are [ADR 0020](adr/0020-app-shell-thin-host-single-instance.md).

## Opening it

```
dettivo app                 # launch, or raise the running window
dettivo app open history    # launch on a route, or route the running window
dettivo app status          # the running window's route, daemon link, first frame, resident set and theme
dettivo-app --open settings.hotkeys
```

The launcher entry is `dettivo.desktop` with the six-bar mark as its icon; its actions open History and Meetings. One window runs per session: a second launch hands its request to the first over `app.sock` beside the daemon socket and exits 0, so a launcher click and `dettivo app open <route>` both land in the window you already have.

Every page carries its title as an accessible name ([docs/qa/a11y-names.md](qa/a11y-names.md)), which is how the drives assert a route opened. A name that is not in this table is refused: `dettivo-app --open garage` and `DETTIVO_E2E_OPEN=garage` exit 2 naming the routes, `dettivo app open garage` exits 4 (the command line's code for bad arguments) naming them too.

Home's Start meeting action opens the same disclosure and recording flow as the Meetings page. A refused dictation start shows its reason in Home. A malformed configuration file leaves the last valid settings in force, which the banner and settings notice state explicitly. Model warm state identifies the loaded model exactly; REST and configured-host summaries use their live sources ([ADR 0056](adr/0056-live-desktop-actions-and-evidence.md)).

On Home, `j` and `k` focus today's items and `Enter` opens the focused take or meeting. The focused row has a theme-derived outline. Settings uses Tab navigation; its footer names the applicable keys.

At narrow widths, Meetings stacks its heading above Search and Import and scrolls its table horizontally. Tab focuses the table; Left/Right move by a spacing step and Home/End reach its first/last columns. The focus outline stays on the viewport. The new-meeting rail scrolls above its configuration footer; its selectable source and fact controls accept keyboard activation. Long analysis scrolls above its footer facts, and a focused action is revealed. During capture, scrolling away suspends transcript following; returning to the end resumes it.

## First run

A fresh machine dictates within three screens, and a provisioned one never sees them (ADR 0024). On every start until a completion is recorded, the app asks the daemon three things: is a speech model ready (`speech.models.status`), does a daemon backend bind the keys (`hotkeys.status`), is the compositor snippet sourced (`hotkeys.setup { write: false }`). A machine with a model and either path for the keys passes, gets `first_run.completed_at` written to the state file and opens Home; any other machine opens `onboarding`. After completion, provisioning reads and the Keys polling timer remain inactive. Explicitly reopening first run reactivates them; closing it stops them. Settings model/hotkey facts and Agents/Doctor diagnostics load when their routes need them. Home reports MCP hosts as "not checked" until every host has been read, then shows configured hosts or "none configured". Models reports "Backend not checked" until its capability query answers; a ready model's runtime state also stays "not checked" until the engine has answered. There is no welcome screen and no other step; `dettivo app open onboarding` reopens the flow on any machine, and a flow closed mid-way reopens on the step it was on.

| Step | What it shows | What it writes |
|---|---|---|
| Keys | The compositor detected, the four bindings with the commands they run, the exact snippet the daemon renders (`hotkeys.snippet`, the same text as `dettivo setup <compositor> --stdout`) and where it goes, and the `Key check` panel that turns into `F9 held · listening · <input>` the moment a press reaches the daemon (a `dictation.state` transition on the compositor path, `hotkeys.status.last_press_at` on the portal and evdev paths). On GNOME, KDE or any desktop without a snippet the box carries the portal's outcome instead. | Continue writes the snippet through `hotkeys.setup` (idempotent; the main configuration is never edited) and reports the include line; Skip writes nothing. |
| Models | The catalogue's shortlist (every model with a `recommended_for` line, plus any model ready or selected) with size, the one-line reason and the readiness, the GPU tier that names the default (`parakeet-v3` on Vulkan, `small.en` on the CPU), the download's progress hairline with the byte count and rate from the `model.download` events, and the optional Enhanced block: the local Qwen3 4B row and `Use Ollama instead` with the probe's answer. Continue is held until the selected model is ready; a failed download names its reason on the row; a model already on disk completes the step at once. | A pick writes `[speech]` through `speech.selection.set` and starts `speech.models.download`; the Enhanced tick writes `[llm] provider` (`local`, `ollama`, or `auto` when unticked). The local model's download runs through `llm.models.download` once the daemon declares it. |
| Try it | `Hold F9, say a sentence, let go.` over a large field; the level bars and the state label (`Listening · Parakeet v3`) follow the stream; the take lands in the field through the real insertion chain, and the three facts under it name the backend, the stop-to-insert time from the completion event's `timings` and the mode. No microphone is said so with the reason, and Done still works. | The field is reachable because the app arms `insert.allow_self_target` while the step is on screen ([docs/insertion.md](insertion.md)); Done disarms it, records `first_run.completed_at` and opens Home; `Open config.toml` opens the file. |

The screens are `qt/qml/Dettivo/app/OnboardingRoute.qml` with `KeysStep`, `ModelsStep` and `TryItStep` over the host's `FirstRunModel` and `FirstRunModels` (`qt/host/app/first_run_model*.{h,cpp}`); every colour, size and spacing is a token, and the three baselines under `docs/design/studio/baselines/first-run-*.png` are held by the visual job ([proving it](#proving-it)).

## Keys

In narrow windows, Settings provides horizontal scrolling for its reference-width tables. Tab and a jump to a configuration key bring the focused editor into view. First run scrolls in shorter windows so its footer remains reachable.

Every screen works without a mouse: Tab and Shift+Tab move through every control on a page in reading order, the focused one carries the shell's focus ring, and Return or Space acts on it. `?` opens the keyboard hint sheet over any page (the in-app keys in two columns, the global ones deferred to Hyprland) and any key closes it. `Super+F` toggles fullscreen, `Escape` leaves fullscreen, closes the hint sheet or a dialog, gives the search field's focus back to the list, or closes a detail back to its list, `/` goes to History and focuses the search (on Meetings it focuses the meetings search), and `m` goes to Meetings from Home. On History `j` and `k` move through the rows, `Enter` opens the row, `r` opens the re-run dialog, `e` the export sheet and `d` the delete confirmation. On Meetings `n` starts a meeting through the rail, `i` opens the import dialog, `j` and `k` move and `Enter` opens; on the live meeting `s` stops after the urgent confirmation; on a meeting `1`, `2` and `3` pick the tabs, `p` toggles Raw and Polished, `r` renames the focused speaker, `t` renames the meeting from its title, `e` exports and `d` deletes. The hint line at the bottom of every page names them ([Meetings](#meetings)). The global keys stay with the compositor ([docs/hotkeys.md](hotkeys.md)). The `keyboard_only` drive proves all of it on every route ([docs/qa.md](qa.md)).

## Designed states

Nothing is ever blank and nothing shouts: every empty, loading and error state is a `StateView` (`qt/qml/Dettivo/app/StateView.qml`) built to `states-and-hint-sheet.png`, the state sentence first in the heading size and emphasis weight, the reason second in muted, the action third as a key cap or a small button, the urgent colour only as the 8 px square, and a loading state shows the shimmer thread with its elapsed time. A `StateView` says whether it follows the rule (`complete`: a sentence, a reason, and an action or a key unless it is loading or declares `actionless` for one of the three states Gordon accepted on 13 September 2026 (`search-no-results`, `microphone-missing`, `insertion-fell-back`)), and the Quick Test holds every sample state to it. The nine states of the sheet render with sample facts and no daemon under `DETTIVO_E2E_STATE` (`history-empty`, `meetings-empty`, `search-no-results`, `engine-loading`, `engine-crashed`, `download-failed`, `microphone-missing`, `insertion-fell-back`, `meeting-recovered`), and `hint-sheet` renders the keyboard hint sheet the same way; the page is the window while it lasts, the state drawn in a bordered box at the artboard's first box, and the visual job holds each to its box on every theme ([docs/design/checklist.md](design/checklist.md), ADR 0042).

## History

History is one timeline with a detail beside it, built to `docs/design/studio/baselines/history.png` (the decisions are [ADR 0025](adr/0025-history-detail-facts-playback-and-export-file.md)). The list column reads `transcripts.list` a page at a time and groups the rows by day (`Today · Wed 3 Sep`, `Yesterday`, `Mon 1 Sep`); a row is the time, one line of text and the meta line (`ghostty · Enhanced · 4 s`), a meeting row carries its `Meeting` chip, its length, its speaker count and its state, and the chips `All`, `Dictation`, `Meeting` and `Import` keep one kind. Typing in the search field runs `transcripts.search` after a short pause (or at once on Enter): the list becomes the hits, the words that matched are painted with the 12 % accent fill, the count beside the query says `3 hits`, and a query with no match says so and keeps the filter. Clearing the query brings the timeline back.

Opening a row (a click, `Enter`, or `dettivo app open history.detail --id <uuid>`) reads `transcripts.get` once and fills the detail: the when line (`Wed 3 Sep · 13:12 · inserted into ghostty`), Enhanced first with the mode that produced it and the insertion outcome, Raw in the light weight, the audio strip, the facts grid and the keys. The facts are what the product promises: the app, the mode, the engine and model, the language, the stop-to-insert time from the completion event (stored with the item since migration `0005-timings`; older rows show a dash), the insertion backend, whether the take is retained (and why not: retention off, or the sweep), and the id.

The audio strip plays the retained take through Qt Multimedia: the 48 bars are the take's own peaks read from the WAV, the played portion is drawn in the accent, a click on the bars seeks, and the clock reads `0:01 / 0:04`. The decoder and sound output initialize on first playback; previewing or seeking the waveform does not initialize them. A seek selected before playback is preserved when the media becomes ready. An item with no take says `Audio was not retained.` or `Audio expired.` in the strip, and Re-run is disabled with the same reason.

Re-run opens a dialog with the engine and the model from `speech.providers.list` (the daemon's selection picked first) and the mode pinned to Raw, and starts `transcripts.rerun`: the linked item appears in the list at once with the progress hairline along its row and the stage in the detail, and settles when `job.progress` reports the end. A second re-run on an item a job is using is refused with the daemon's `CONFLICT`, shown in the dialog. Export opens a sheet with the format (JSON, Markdown, Text, Archive with audio) and the scope (this dictation, or everything), and writes the file through a download transfer to the place the desktop's save dialog names (`org.freedesktop.portal.FileChooser`); a refused export names the daemon's reason in the sheet. Delete is text in the urgent colour at the foot of the detail; it asks once, removes the item per `[history] artifacts` ([docs/history.md](history.md)), and the list drops the row without a reload.

**Copy transcript** copies the displayed final text, falling back to raw text when no final text exists. Switch to the destination app and paste with Ctrl+V (Ctrl+Shift+V in terminals). The copy leaves the original insertion outcome unchanged. The global reinsert shortcut still inserts the last dictation into the app focused when you press it.

## Meetings

Meetings are three screens over the daemon's meeting lane, built to `docs/design/studio/baselines/meetings-list.png`, `meeting-live.png`, `meeting-detail.png` and `import-and-disclosure.png` (the decisions are [ADR 0038](adr/0038-meetings-gui-live-events-pause-gap-and-inline-dialogs.md); the daemon side is [docs/meetings.md](meetings.md)).

**The list** (`meetings`) reads `meetings.list` a page at a time and groups the rows by week (`This week`, `Last week`, `Week of 25 Aug`); a row is when the meeting started, its title with the one-line summary the analysis wrote, its length, the speakers as swatches in the speaker colours with their names (read from `meetings.get` for the rows that have any), and a chip that names its state (`Analysed`, `Partial`, `Notes only`, `Transcript`, `Recording`, `Transcribing`, `Failed`). Recover follows the server's recoverable list for retained partial, failed, cancelled or stopped input; Discard remains partial-only. Transcribing rows offer Cancel transcription through `meetings.cancel`. Terminal job events refresh the row and its recovery action, and cancelled/stopped rows show those states explicitly. Typing in the search field runs `meetings.search` over the title, the transcript, the speakers, the notes and the analysis. The rail on the right is the new meeting: the two sources with their device names and the level bars that follow `audio.level` per source while a meeting runs (the microphone always records; System audio can be left out), the engine and model from the meeting-capable providers of `speech.providers.list` (a menu on the row; Parakeet stays dictation-only), the expected speaker count (a field on the row; empty lets the clustering decide), the analysis after the stop (a toggle), the disclosure state with its copy action, and `Start meeting`. The engine choice writes the daemon's selection the way Settings does (`speech.selection.set` for another provider, `[speech] meeting_model` for a model of the selected one); the speaker count goes on the start request alone, and the analysis toggle starts on `[meetings.analysis] auto` and goes on the request only once you change it, so an untouched rail runs on the configuration. The footer names `[meetings]` in `config.toml` as what sets the defaults and opens the Meetings settings section (`speech.meeting_model`, `meetings.diarization.max_speakers`, `meetings.diarization.auto`, `meetings.analysis.auto`, `meetings.delete_artifact_policy`).

**Starting one** reads `meetings.disclosure.get` first. A profile that has not acknowledged the recording disclosure gets the dialog with the macOS message verbatim, `Copy message`, `Not now` (the list stays and nothing starts) and `Acknowledge and start`, which puts `acknowledge_meeting_disclosure` on the `meetings.start` request; the daemon records it once and the dialog never shows again, and the rail's disclosure row reads `acknowledged 11:04` with the copy action. A start the daemon refuses names the gate from its `CONFLICT` under the column labels (`sessionActive`, `engineWithoutTimestamps` with the settings route to fix it, `meetingDisclosureRequired`).

**The live meeting** (`meetings.live`) shows the recording square, the title, both source meters with their device and app names, the elapsed time as the largest type on screen, `Pause` and `Stop`. Pause is disabled: the contract has no pause verb, and the button's accessible description says so. The transcript follows the `meeting.segment` events: a row is the time on the wall clock, the source label in its speaker colour (`You` first, `Remote` second) and the text at a 1.7 line height; a provisional segment reads in the light weight and the muted colour until a later window finalises it, a capture gap draws a hairline with its length, and the footer says that speakers are labelled by source until the diarization pass names them, with the segment and gap counts on the right. The rail holds the notes, a Markdown editor with a live caret whose text reaches `meetings.notes.set` with `source = live` a second after the last key and stays yours until the daemon has acknowledged it (a refused or unanswered save is retried, a reload never overwrites the draft, and closing the app sends what is pending), the analysis card that says when the analysis runs and that it never overwrites the notes, and the disclosure state with `copy message`. `Stop` (and `s`) asks once with the urgent text; the moment the stop is sent the square turns muted, the elapsed display freezes on the recorded length, the meters give way to `Recording stopped` with the stage (`Stopping · closing the takes`, then `Transcribing · 18 of 22 chunks` from `job.progress`) and a progress bar that sweeps until the chunks are counted, and the footer says the meeting opens when the transcript is ready; a stop the daemon refuses reads there in the urgent colour and the recording goes on. The screen lands on the detail when the meeting is `completed` (ADR 0061). A meeting started from the bar or the command line is adopted from its first `recording` event; a daemon restart mid-meeting keeps the segments on screen, and the reconnect reads the meeting back and lands on the partial row when the daemon promoted it.

**The detail** (`meetings.detail`, `--id <uuid>` names the meeting) reads `meetings.get` once: the title (a click, Return on it or `t` turns it into a field prefilled with the current title; Return saves through `meetings.rename` and relabels the header and the list row, Escape keeps the saved name, a refusal reads under the field with the edit kept) with `Re-run` (disabled; a meeting re-run stays reserved in the contract and the description says to import the audio again instead) and `Export`, the facts line (`Wed 3 Sep · 11:05 to 11:46 · 41 min · whisper small · diarized · analysed`; a partial meeting adds `Recovered after a crash · 12 of 14 chunks`), the processing strip (`Transcript ready · speakers running` while a pass is still to come, one dot and state per stage, a progress bar under the running one that sweeps until it has a chunk count; once every stage settled the strip stays, muted, with the outcome and each stage's facts: `Processing complete` over `948 segments`, `3 speakers · 154 segments unassigned` (the segments the pass left labelled by source) and the analysis model and time; `Processing complete · analysis not run` when a pass was switched off; `Processing incomplete · speakers skipped, no speaker model downloaded` in the highlight colour when a wanted pass had nothing to run on; `Processing finished · analysis failed` in the urgent colour), the talk-time bar split by each speaker's `talk_ms` with the legend of name, time and share, and the three tabs. Transcript shows every segment with its speaker in its colour and the `Raw · Polished` toggle between the engine's words and `polished_text`; Notes is the same Markdown editor saving with `source = user`; Analysis carries the summary, the decisions and the action items at reading width with `Analyse again` (`meetings.analyze { force }`) and `Run speakers again` (`meetings.diarize`). The rail on the right is the analysis with the model and the time, the summary, the decisions and the action items, and at its foot the notes, export and audio facts; a meeting without an analysis says why and offers to run it. A click on a name in the bar or the transcript (or `r` on the focused speaker) opens the rename popover under it: the name field, the remembered names from `meetings.speakers.suggest`, Enter applies through `meetings.speakers.rename` and every row relabels at once, Escape cancels, an empty name restores the label. `Export` opens the sheet with the five formats (`md` with the notes and the analysis, `txt`, `srt`, `vtt`, `json`) and the engine's words as an option, and writes the file the way History does (the portal's save dialog, or `DETTIVO_E2E_EXPORT_DIR`). `delete meeting` is text in the urgent colour in the footer; it asks once naming what `[meetings] delete_artifact_policy` removes and what stays, and the list drops the row without a reload.

**Import** (`Import audio`, `i`) maps one to one onto `transcripts.import`: the file (a path in the field; once it is a file the line reads its name, length and size), the target kind, the engine, the language, `diarize after transcription` and `summary, decisions, action items`, the sentence on the chunking (5 minutes with 2 s overlap) with the estimate from the file's length, and `Import`, which uploads the file through a transfer, starts the job with the disclosure acknowledged, follows `job.progress` on the row and opens the detail when the job ends. A file the daemon rejects names the daemon's reason in the dialog.

In the history timeline a meeting row carries its `Meeting` chip and, from the same page, its length, its speaker count and its state (`41 min · 3 speakers · analysed`).

The screens are `qt/qml/Dettivo/app/meetings/` over the host's `MeetingsModel`, `MeetingLiveModel` with `LiveSegmentsModel`, `MeetingDetailModel` and `MeetingsActions` (`qt/host/app/`); every colour, size and spacing is a token, and the four baselines are held by the visual job region by region on every theme ([proving it](#proving-it)).

## Settings

Settings edits the same `config.toml` as the CLI ([configuration guide](config.md), [ADR 0033](adr/0033-settings-routes-config-editor-key-registry.md)). Simple mode shows everyday controls. The shared **Show advanced settings** toggle reveals technical settings, generated snippets and TOML previews across all nine sections, including Agents. Each editable row offers **Reset**, with its canonical default in the tooltip. Environment overrides stay locked and refused writes show their reason inline.

Use labeled language and model menus, individual Polish transforms, and the dedicated Vocabulary page to add or remove whole terms. Unavailable or custom model selections remain visible. Advanced experimental model settings follow the supported [polish experiment workflow](polish-models.md); they do not make arbitrary model files compatible. The commented reference ships at `/usr/share/doc/dettivo/config.example.toml` and is also available through `dettivo config print-default`.

The route follows the file: a hand edit, `dettivo config set` or `dettivo config unset` reaches the open section through the daemon's `config.changed` event, the rows refresh and the line under the title says `The file changed on disk; 1 value(s) refreshed.`; a field you are typing in keeps your text and says what the file now holds. `dettivo app open settings.<section> --id <key>` opens a section scrolled to the row that edits a key.

| Section | What it edits |
|---|---|
| General | `[daemon]`, `[audio]`, the dictation session (`[dictation] language`, `vocabulary`, the longest take, the silence threshold), `[paths]`, the recording pill (`[osd]`) and the Omarchy plugin (`[omarchy]`) |
| Hotkeys | The four chords as editable rows with their key caps, the snippet the daemon renders from them (`hotkeys.snippet`, the same text `dettivo setup <compositor> --stdout` prints) with `Rewrite snippet` and `Copy include line`, and the panel: the daemon backend, media pause, the sounds, the evdev devices ([docs/hotkeys.md](hotkeys.md)) |
| Models | The dictation model, the meeting model, the Enhanced model and the idle unload over `[speech]`, `[llm]` and `[engines]`; the table of every speech and language model with its size, backend, state and actions (`Download`, `Cancel`, `Delete`) from `speech.models.status` and `llm.models.status`, live through the `model.download` events; the engine backends and the catalogue keys below ([docs/models.md](models.md)) |
| Polish | The dictation mode, spoken punctuation, replacements and protected tokens, the Polish pass (transforms, default preset and style), the Enhanced providers and the sideloaded experiments over `[llm]` ([docs/polish.md](polish.md)); rules and app profiles are edited with `dettivo polish` |
| Insertion | The chain over `[insert]`: the backend, the paste keys and the app id lists, the clipboard restore and the undo window ([docs/insertion.md](insertion.md)) |
| Meetings | The meeting and analysis models, the history store (`[history]`), the chunked pipeline (`[transcribe]`), the upload limit, the capture and live transcription keys (`[meetings]`, `[audio] system_source`) and the recording disclosure with `Copy message` |
| Agents | The socket and its auth from `[ipc]`, the REST shim's facts, the four MCP hosts with the file each reads and whether Dettivo's entry is in it (`Write config` runs `dettivo mcp config --host <id> --write`, the same code as the terminal), the entry a host receives, the `[ipc]`, `[mcp]` and `[rest]` keys ([docs/mcp.md](mcp.md), [docs/rest.md](rest.md)) |
| Diagnostics | `dettivo doctor` on screen, line by line with the exit code as the verdict, `Run again` and `Copy report`, and the `[qa]` switch |

The sections are `qt/qml/Dettivo/app/settings/` over the host's `SettingsModel` (values, sources, the registry from `config.keys`, writes, the TOML block, the refresh), `ModelsTable`, `HotkeysSetupModel`, `AgentsModel` and `DoctorModel` (`qt/host/app/`); the keys each section edits are one table, `qt/host/app/settings_keys.cpp`, which the drive and `scripts/lint-settings-keys.sh` read too. Models, Hotkeys and Agents are held to `docs/design/studio/baselines/settings-models.png`, `settings-hotkeys.png` and `agents.png` region by region; General stands for the five sections that follow the pattern ([proving it](#proving-it)).

## What the window reads

| Surface | Source |
|---|---|
| Daemon link, health, the status sentence | `system.health`, `system.version`; the sentence is `Ready.`, `Listening.`, `Transcribing.` or `Inserting.` from `dictation.status` and the `dictation.state` events, `Daemon unavailable.` while the socket does not answer, `Configuration needs attention.` while `config.toml` does not parse |
| The hotkeys in the sentence | `config.get` (`hotkeys.hold`, `hotkeys.toggle`), shown as `F9` and `Super+Ctrl+X` |
| The target app in the sentence | `insert.target` (the focused window's app id, shortened to its last segment) |
| Mode segment | `config.get` and `config.set` on `dictation.mode`; the file stays the source of truth |
| Input and the waveform | `audio.devices` (the pinned or default source's description) and the `audio.level` events |
| Today | `transcripts.list`, paged with the daemon's cursor; the newest day's rows, labelled `Today`, `Yesterday` or the date |
| Engines | `speech.engines` and `speech.selection.get`, kept current by `engine.state`, `job.progress` and `model.download`; the selected speech engine comes first, then the other one, the language model and diarization, each `warm`, `idle`, `loading`, `downloading`, `cpu`, `crashed` or `not installed`, with the 2 px hairline filling while it loads |
| Agents | `system.capabilities` (the socket mode, the REST shim's state); the MCP hosts and the last call arrive with the agents spec |
| Sidebar footer | The selected speech engine, the language model and the socket mode from the same answers |

The daemon may come and go: the client reconnects with a backoff from half a second to eight, the banner `Daemon unavailable.` with the `systemctl --user start dettivod.socket` hint appears once the daemon has been away for a second and a half and clears the moment it answers, every fact is re-read on reconnect, and the window never goes blank.

## QA variables

With QA mode on ([docs/qa.md](qa.md)):

| Variable | Effect |
|---|---|
| `DETTIVO_E2E_OPEN=<route>` | Opens a route from the table above (`settings.<section>` for a section). |
| `DETTIVO_E2E_ROUTE=<section>` | With `DETTIVO_E2E_OPEN=settings`, the section to open. |
| `DETTIVO_E2E_SEED=1` | Passed through to the daemon the drive starts, so Today has rows. Under `--render` with no daemon it fills the models with the baseline's sample, the same as `--sample`, which is how the visual manifest renders Home, History and the first-run steps. |
| `DETTIVO_E2E_COMPLETE=1` | First run is marked complete: the check never runs and Home opens. |
| `DETTIVO_E2E_STEP=keys\|models\|try` | Opens first run on that step whatever the check would say. |
| `DETTIVO_E2E_EXPORT_DIR=<dir>` | The export sheet writes the file into this directory under the daemon's file name instead of opening the portal's save dialog. |
| `DETTIVO_E2E_STATE=<state>` | Renders one designed state or the hint sheet with sample facts at the artboard's first box ([designed states](#designed-states)): the nine states of `states-and-hint-sheet.png` and `hint-sheet`. |
| `DETTIVO_E2E_MEETING_STATE=<state>` | Opens one meetings screen: `list`, `list-empty`, `live`, `detail-transcript`, `detail-notes`, `detail-analysis`, `rename`, `import` or `disclosure`; the route follows the state and, under `--render` with `DETTIVO_E2E_SEED=1`, the screen carries the baseline's sample (the six rows of `meetings-list.png`, the kickoff of `meeting-live.png` and `meeting-detail.png`). With `DETTIVO_E2E_OPEN=meetings.detail`, `DETTIVO_E2E_ROUTE=<meeting-id>` names the meeting. |

Under QA mode the app also appends one JSON line per fact a drive reads back to `$XDG_STATE_HOME/dettivo/qa/app.jsonl`: `first_frame` (milliseconds from the process start and the resident set), `theme_applied` (milliseconds from the theme file change to the frame that carried the new palette, with the source and the accent) and `idle` (the resident set after five seconds).

`dettivo-app --render <png> --sample --open home` writes the Home route headlessly at 1280 by 820 with the baseline's sample facts and no daemon, which is what the visual check compares with the approved crops; `--open history` renders History with its newest sample row open, `DETTIVO_E2E_OPEN=onboarding DETTIVO_E2E_STEP=<step> DETTIVO_E2E_SEED=1 dettivo-app --render <png>` does the same for a first-run step, and `DETTIVO_E2E_MEETING_STATE=<state> DETTIVO_E2E_SEED=1 dettivo-app --render <png>` for a meetings screen.

## The state file

Runtime state that is not configuration lives in `$XDG_STATE_HOME/dettivo/state.toml` and never in `config.toml` ([docs/config.md](config.md)):

| Key | Meaning |
|---|---|
| `[window] width`, `height`, `x`, `y`, `maximized` | The window's last geometry, restored on the next start |
| `[app] last_route` | The route the window was on when it closed, opened on the next start unless a route was asked for |
| `[app] last_meeting_tab` | The detail tab a meeting reopens on (`transcript`, `notes`, `analysis`) |
| `[first_run] completed_at`, `step` | When first run finished (ISO 8601 UTC, empty until it does) and the step a flow closed mid-way was on, so it reopens there ([the first-run section](#first-run)) |

The daemon keeps `[daemon]` and `[acknowledgements]` in the same file; each writer carries the other's tables through untouched (ADR 0024). A file that does not parse is reported once on standard error and replaced on the next save.

## Theme

On Omarchy the palette, the control states, the font and the spacing come from the active theme's `colors.toml` and `shell.toml` under `~/.local/state/omarchy/current/theme` ([qt/qml/Dettivo/README.md](../qt/qml/Dettivo/README.md)). `colors.toml` alone is a theme: a shell token the theme does not name takes the theme's own role (the bar is the background, a pressed control is the accent), the way Omarchy's generated `shell.toml` fills it, so a theme without one still renders as itself. The app watches the files and the `current` directory, so `omarchy theme set`, which replaces the directory, re-skins the window on the next frame; `DETTIVO_OMARCHY_THEME_DIR` points it at another directory. Off Omarchy the built-in dark and light palettes follow the portal's `color-scheme` setting, and the portal's reduced-motion preference cuts the transitions. A theme file that does not parse falls back to the built-in palette and is reported once. `dettivo app status` prints a `theme` block (`source`, `dir`, `background`, `accent`, `parse_error`), so a window in an unexpected palette says which files it read and why it fell back.

The window chrome is the compositor's: on Hyprland and the other wlroots compositors the xdg-decoration negotiation gives server-side decoration, so the window has none of its own and the compositor rounds and borders it like every other window; fractional scaling follows the compositor's `wp_fractional_scale_v1` with the scale factor passed through unrounded.

- `just test-qt` runs the host tests (`qt/host/app/app_host_test.cpp`: the router, the state file, the formatting, the models against a fake daemon link, the instance socket, the portal colour-scheme switch; `app_history_test.cpp`: the list's search, jobs and removals, the kind filter, the detail's facts, the actions through a fake link into the QA export directory, the player's bars from a WAV; `app_meetings_test.cpp`: the meetings list's weeks, chips and swatches, the live transcript's tail fragment by fragment, the live model's disclosure gate, start, levels and the stop acknowledged at once; `app_meeting_detail_test.cpp`: the detail's facts, shares, rename, title and processing stages, the actions' upload import, retitle and delete policy), the Quick Tests for the screens (`qt/qml/Dettivo/tests/qml/tst_app_shell.qml`, `tst_app_home.qml`, `tst_app_history.qml`, `tst_app_meetings.qml`, `tst_meeting_detail_processing.qml`), a headless load of every route with its title, the refusals of an unknown route, and the app's render with the negative style check (`dettivo-app-render` and the two planted checks, ADR 0021). Home's four regions are held to `home.png` by the visual matrix (`qa/visual/manifest.toml`, the `home` surface) on every theme and scale like every other surface.
- `just qa-drive first_run_fresh atspi|cua` walks a fresh profile through the three screens against a daemon with the real insertion chain: Keys shows the snippet `dettivo setup hyprland --stdout` prints and confirms a press made through the daemon, Continue writes it once, the Models rows come from the catalogue and a pick writes `[speech]` and downloads the test model from a loopback fixture server, Try it dictates the mock microphone into the field and names the backend and the time, and Done records the completion and opens Home (`first-run.json`, `snippet.conf`, a screenshot and tree per step). `first_run_provisioned` gives a profile a sourced snippet and a ready model and sees Home with no first run and the completion recorded. Anonymous memory includes heaps and stacks allocated by Qt and drivers as well as Dettivo.
