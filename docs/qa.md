# QA rig

Every user-facing behaviour gets an automated way to prove it works on a real desktop, and that proof runs in CI without a microphone or a person at the keyboard (ADR 0011). The rig has four parts: a driver that finds and acts on real windows through the accessibility tree, a headless display in CI, a virtual audio rig that feeds real audio into the real capture path, and the QA switches inside the product that make a run deterministic.

## Running it

The [2026-09-08 live desktop report](reports/qa/2026-09-08-live-desktop.md) records the post-cleanup fixes, running-window evidence, visual differences and installed-session limits for fn-54. Its memory failure remains historical evidence under the original requirement. [ADR 0059](adr/0059-desktop-memory-budgets-follow-measured-reference-profiles.md) defines the replacement contract, with fresh results in the [2026-09-10 desktop memory report](reports/qa/2026-09-10-desktop-memory.md).

The [follow-up beauty iteration](reports/qa/2026-09-08-beauty-iteration.md) records direct artboard comparisons, compact-window regressions and the subsequent verification on PR #53.

```
just qa                                  # contract replay, the drive pack, the lints
just qa-evidence-map                     # every spec's R-IDs mapped to routes that exist, docs/reports/evidence-map.md (docs/guides/qa.md)
just qa-release                          # the optional deep gate: thirteen named steps, one report under docs/reports/release-gate/ (docs/RELEASING.md)
just qa-drive placeholder_window atspi   # one scenario on one driver (cua|atspi)
just qa-pack dictation                   # the dictation slice in order, one report (the release gate's first step)
just qa-pack gui                         # the four GUI surfaces on both drivers with the scans per route (the gate's second step)
just qa-pack-meetings target/vulkan/debug   # the meeting lane end to end with the throughput report, filed under docs/reports/benchmarks (the gate's third step)
just qa-pack-meetings-cpu                # the same pack on the CPU tier with base.en (the CPU-only VM's command)
DETTIVO_BUILD_PROFILE=release just qa-pack gui   # after `just build-release`: the drives take target/release, never the newer build
just qa-contract                         # the fixture suite against a fresh daemon
just qa-audio                            # the virtual audio round trip (needs PipeWire)
just qa-visual                           # every surface against its approved baseline (optional, run it when you want to look; ADR 0066)
just qa-visual-canary                    # the same renders with a deliberate regression; must fail
just qa-visual-approve osd --theme tokyo-night   # a fresh render becomes the baseline, recorded
just qa-beauty                           # every surface on the five palettes as contact sheets, with the checklist's machine verdicts (ADR 0042)
dettivo-qa doctor                        # names the missing piece: display, session bus, a11y bus (it connects, so a dead socket is named), tools
```

On a Hyprland desktop the Qt binaries run under `QT_QPA_PLATFORM=xcb` (XWayland) so both drivers can see them. In CI, and on a desktop where a drive must stay off the live screen, `scripts/qa/xvfb-session.sh` starts Xvfb, a session bus, the accessibility bus and a window manager around the same commands. That session is an X11 desktop whatever started it: it drops the caller's `WAYLAND_DISPLAY` and `HYPRLAND_INSTANCE_SIGNATURE` so the daemon probes the drive's own window rather than the live compositor's, and its bus activates no service, so a token lookup through `secret-tool` or a portal probe returns at once instead of waiting out the 120 s activation timeout.

Every scenario runs in an isolated profile: its own `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_DATA_HOME` under one scenario root, a private models directory with only the test models (`whisper/tiny.en`, `fixtures`) linked in from the real directory (the weights as hard links, the manifest and any partial download as copies) so nothing downloads twice and nothing a daemon deletes or rewrites reaches the user's models (a scenario that needs another model names it through `Scenario::models`, and the runner links it by name before the daemon starts or skips the scenario naming the model and the command that fetches it), and a `config.toml` that pins `[hotkeys] backend = "none"` so the desktop's portal never binds shortcuts for a scenario's daemon. `XDG_RUNTIME_DIR` is inherited on purpose, because the session bus, the accessibility bus, the display and PipeWire live there; the daemon is isolated through `DETTIVO_IPC_SOCKET` under the scenario root instead. When the scenario ends the runner checks that no process it started is still alive and no socket is left under the root, and it fails naming anything that leaked. A profile root that would resolve under the caller's `HOME` or a real `XDG_CONFIG_HOME`, `XDG_STATE_HOME` or `XDG_DATA_HOME` is refused before anything starts, naming the variable, and so is a models tree that is the real models directory or under it, by path and through symlinks: a drive never links a real user directory, so a first-run drive never sees the developer's snippet, models or state, and the only thing shared with the machine is the hard-linked test model (the tree lives under `target/qa-models/<profile>` on the models' filesystem, where a link is a hard link rather than a copy into the `/tmp` root; [ADR 0043](adr/0043-qa-profiles-carry-a-private-models-directory-and-the-gate-passes-on-what-the-code-does.md)).

Evidence lands under `qa-evidence/<run>/<scenario>.<driver>/` (one directory per driver, so both drivers' outputs sit side by side): `screenshot.png`, `tree.json` (the accessibility snapshot), `receipt.json` (scenario id, driver, outcome, timings, evidence paths) and the daemon and app logs.

## The dictation pack

`dettivo-qa pack dictation` runs the dictation slice in one order, in one evidence run, and writes one report (ADR 0017). `dettivo-qa pack list` names every pack with its steps; `just qa-pack dictation` runs it after the build. The steps, in order:

| Step | Driver | Expectation |
|---|---|---|
| `hotkeys_hyprland` | any (drives the compositor and the socket) | skip allowed: no `hyprctl`, no Hyprland session, no writable `/dev/uinput` |
| `osd_dictation` | `atspi`, then `cua` | skip allowed: no display, no accessibility bus, no `cua-driver` |
| `insertion_matrix` | `--driver` (default `atspi`) | skip allowed; a target the machine lacks is a skipped row, never a failure |
| `never_into_self` | `--driver` | skip allowed |
| `history_roundtrip` | any (drives the socket) | must pass |
| `first_insert_timing` | `--driver` | skip allowed |
| `whisper_wer` | none (the engine binary) | must pass: the engine transcribes `jfk.wav` with `tiny.en` under a word error rate of 0.15, on the CPU under CI (`--cpu`) and on the backend the engine was built with elsewhere (`just build-whisper-vulkan` for the Vulkan figure) |

A step skipped for an allowed reason is recorded with the reason and the pack continues; a hard failure (a failed step, or a skip on a must-pass step) stops the pack and marks every later step `not_run` naming the failed step, unless `--continue` runs them anyway. The report is written either way, so the evidence is never lost. Exit 0 means every step passed or skipped for an allowed reason, 1 a hard failure, 2 a preflight refusal (an unknown pack name, which lists the packs; an unbuilt `dettivod`; an unwritable evidence directory).

The report lands under `qa-evidence/<run>/pack-dictation/` beside the steps' own directories: `dictation-pack.json` for the release gate and the flow-next QA pass, `dictation-pack.md` for a person. It names the machine (host, compositor, session, GPU and insertion backend from `system.capabilities`) and the tier (`gpu` when the Whisper engine reported Vulkan, `cpu` otherwise); one row per step with outcome, duration, evidence directory and reason; the measurements; and the blockers, one per step that could not run with the doctor's failed checks first. Under CI the report says the NFR figures are recorded and never gated; on the development machine the comparison is recorded too, and the release notes quote it ([docs/RELEASING.md](RELEASING.md)).

`dettivo-qa pack release` is the release gate: it runs this pack, the GUI pack and the meetings pack as three of its thirteen steps beside the strict contract replay, the MCP harness, the visual matrix, the benchmark and install-test reports, the evidence map, the docs build and the notice lint, embeds every report and names every blocker ([docs/guides/qa.md](guides/qa.md#the-release-gate), [docs/RELEASING.md](RELEASING.md), [ADR 0041](adr/0041-guides-docs-build-evidence-map-and-the-release-gate-script.md)).

The measurements:

- **Time to first insert (NFR-1 on the GPU tier, NFR-2 on the CPU tier):** p50 and p95 of the stop-to-completion path over the ten warm runs of `first_insert_timing`, the cold run listed and excluded, split at p50 into capture, transcribe and insert. The target comes from `crates/dettivo-qa/src/nfr.rs`, the one place the calibrated targets live ([ADR 0029](adr/0029-nfr-calibration-and-the-benchmark-suite.md)); the report names the NFR it was held to.
- **Insertion reliability (NFR-3):** passes over attempted rows of the insertion matrix against 0.98. Skipped targets are excluded from the figure and listed with their reasons; a failed target is listed with its backend and reason.
- **Whisper WER:** the rate against the 0.15 threshold, with the backend and model that ran.

## The GUI pack

After every scenario step the pack scans each `tree-<route>.json` the step captured and fails the step naming the route, the class and the element:

- **Developer text.** Every accessible name goes through the eight classes of `crates/dettivo-qa/src/negative_text.rs`: exception text (`Exception`, `Traceback`, `panicked`, `unwrap()`), a stack-trace frame (`.rs:`, `.cpp:`, `.qml:` or `.h:` followed by a line number), raw JSON (a name that parses as an object or array), a raw path (`/home/`, `/tmp/`, `/usr/`, `/var/`, a bare hidden directory), a model file name (`.gguf`, `.bin`, `.onnx`, `ggml-`, `.safetensors`), an internal identifier (`fn-<n>`, `TODO`, `FIXME`, `XXX`, `lorem ipsum`, `placeholder text`, `parity_gap`), the word `debug` inside a sentence (the bare `debug` log level is a value, not a sentence), and a hash or an address (32 hex digits, `0x` and six). The one exemption is the drive's own profile root under `/tmp/dq`, the rig's location shown back; text that arrives from the daemon fails the route and is fixed in the product, never allowlisted.
- **Accessible names.** Every element on screen whose role a user acts on (`push button`, `toggle button`, `check box`, `radio button`, `text`, `combo box`, `slider`, `spin button`, `page tab`, `list item`, `menu item`, `link`) must carry a non-empty name; static text and images are exempt, and a control with no bounds is not on screen. The walk writes `a11y-<route>.json` beside the tree with the interactive count, the named count and every offender by role, index and bounds.

The report lands under `qa-evidence/<run>/pack-gui/` as `gui-pack.json` and `gui-pack.md` (a per-surface pack writes `gui-<surface>-pack.json`), in the ADR 0017 shape plus `surfaces`: one block per surface with its steps and outcomes, `negative_text.routes` (how many trees were scanned) and `negative_text.findings` (each located by step, driver and route), and `a11y_coverage` as named over interactive with the offenders listed: `1.0` for an inspected screen with no control, `null` (`not inspected` in the Markdown) for a surface whose steps captured no tree. The figure the gate reads is `a11y_coverage = 1.0` on every surface with an empty findings list; a GUI step that passed without capturing a tree fails as not inspected, an empty or unreadable capture is a finding by name, the plain `tree.json` of a one-screen scenario is scanned as the `window` route, and a control whose geometry the driver could not read counts as on screen and has to carry a name ([ADR 0051](adr/0051-the-release-gate-passes-on-validated-evidence-bound-to-the-tested-binaries.md)). The `binaries` block names every binary the pack drove with its profile (`release`, `debug`, or `qt` for the CMake tree, built Release), and `qa_allow_release` records that every profile sets `DETTIVO_QA_ALLOW_RELEASE=1` so a release binary accepts QA mode. A drive launches `target/<profile>/` for `DETTIVO_BUILD_PROFILE` (`debug` unless it says `release`; the release gate pins `release` and records each binary's SHA-256 and the commit the CLI embeds), never the newer of the two builds; under CI the drive job runs `just build-release` and then the pack with the variable set, so the scan holds on release routes on every push; the Omarchy desktop steps and the `cua` steps without the tool are the allowed skips the blockers list names. The weekly job runs the pack on the fallback driver with no `cua-driver` installed.

## The meetings pack

`dettivo-qa pack meetings` runs the meeting lane in one order, in one evidence run, and writes one report ([ADR 0039](adr/0039-meetings-pack-finalisation-path-throughput-and-the-gpu-proof.md)): the capture spec's rig scenario, the kill and recovery, the live transcript, diarization against the turns golden, the export goldens, the three meetings screens on both drivers, the two-voice token fixture, and then the throughput measurements for NFR-4 and NFR-5 with the proof that a GPU run did its work on the GPU. `just qa-pack-meetings target/vulkan/debug` runs it after the build with the Vulkan Whisper engine and files the figures; `just qa-pack-meetings-cpu` is the same pack on the CPU tier, the command the CPU-only VM runs. The steps, in order:

| Step | Driver | Expectation |
|---|---|---|
| `meeting_rig` | any (the rig and the socket) | must pass where PipeWire runs; without it (a container) an allowed skip the blockers name, and the mock steps below carry the capture path |
| `meeting_recovery`, `meeting_live` | any (the socket) | must pass: SIGKILL and recovery with the transcript over both takes; the live transcript against the interleave golden |
| `diarization_der` | none (`dettivo-qa pipeline diarization`) | must pass: two speakers, error rate under 0.20; an absent model set fails naming `scripts/models/fetch-diarization-model.sh` |
| `meeting_export_goldens` | none (`cargo test -p dettivo-storage --test meeting_export`) | must pass: the five formats byte-equal to their goldens |
| `meetings_seeded`, `meetings_live_gui`, `meetings_import_gui` | `atspi`, then `cua` | the `atspi` step must pass; the `cua` step may skip without `cua-driver` |
| `meeting_token_coverage` | any (the rig or the mock variables, and the socket) | must pass: every alpha token on its source, two speakers, both names in the `md` export |
| `meeting_throughput` | none (a daemon in its own profile) | must pass: the five-minute import completes with a transcript; the realtime factor is recorded against NFR-4 or NFR-5 and never gated |
| `diarization_throughput` | none (`dettivo-engine-diarize`) | must pass: the same system track diarized; records the actual `backend`, optional `fallback_reason`, `engine_pid` and factor against NFR-4's four times realtime |
| `gpu_workload_proof` | none | Unsupported inference attribution is unavailable; process presence and aggregate activity are diagnostic. Required CUDA proof cannot pass on those observations alone. |

**The token rule.** `crates/dettivo-qa/fixtures/meetings/alpha.mic.wav` is Alice (Piper `en_US-amy-low`) and `alpha.system.wav` is Ben (`en_US-ryan-low`), rendered once by `scripts/qa/make-alpha-fixture.py` from the script in `alpha.script.txt`, Ben answering after Alice has finished so no cross-source suppression applies; `alpha.tokens.json` names each token with the source it belongs to. Every token must appear among the words of that source's finalised segments, the speaker pass over the system track (the count pinned to one) must leave the row with two speakers (`You` and the one it found), and after `meetings.speakers.rename` names them Alice and Ben the `md` export must carry both before a transcript line. A failure names the token and its source, and `transcript.json` and `meeting.md` sit in the evidence.

**The throughput method.** `meeting_throughput` builds five minutes of meeting audio under its step directory (the alpha microphone track, a second of silence, then the jfk clip with a second of silence after each copy), uploads it through `transfer.begin`, `transfer.chunk` and `transfer.commit`, and imports it with `transcripts.import { target_kind: "meeting", provider: "whisper", model, diarize: false, analyze: false }` on a daemon whose profile links the models in and pins `[speech] model` and `meeting_model`, so the chunked pipeline, the overlap merger, the filler filter, the polish pass and the store are all timed. The realtime factor is the audio length over the wall time from the job's first `job.progress` at `stage = decoding` to `done`; `speech.engines` gives the engine's backend and reason, `system.capabilities.platform` the tier, and `crates/dettivo-qa/src/nfr.rs` the target by tier. The harness's own CPU share is measured with the daemon idle before the import and again during it, and a share over ten percent is recorded as a warning beside the figure. `diarization_throughput` runs `dettivo-engine-diarize --wav <the system track> --model <the set> --speakers 1 --json` and records its factor the same way. The engine binaries come from `--engines <dir>` (the Vulkan build for the GPU figure) or the workspace build.

**The GPU proof.** A sampler records engine process IDs, NVIDIA process-table presence and AMD aggregate activity during the import. Those counters show allocation or device activity but do not attribute inference to the measured engine. `gpu-samples.json` retains them as diagnostics; workload proof is unavailable when attribution is unsupported. A required CUDA diarization proof still rejects a missing or wrong engine PID and also fails when attribution is unavailable ([ADR 0054](adr/0054-delete-duplicate-work-and-keep-one-owner.md)).

**The CPU path.** `--cpu` sets `DETTIVO_FORCE_CPU=1` for every daemon and engine the pack drives (the scenario steps get it through their profile's environment) and transcribes with `base.en`, the NFR-5 model, unless `--model` names another catalogue id; an unknown id exits 2 naming the Whisper ids the catalogue offers, and a model not on disk fails the step naming `dettivo speech download`. An engine that still reports the Vulkan backend under `--cpu` fails the step by name. The same command on this desktop records the CPU tier and on the CPU-only VM records that machine; the report names the host and the tier, so the two rows never merge.

**The report.** `qa-evidence/<run>/pack-meetings/meetings-pack.json` and `meetings-pack.md` carry the ADR 0017 shape plus `measurements.meetings`: `meeting_rtf`, `meeting_rtf_nfr`, `meeting_rtf_target`, `meeting_rtf_met`, `diarization_rtf`, `diarization_rtf_target`, `diarization_rtf_met`, `tier`, `engine`, `model`, `backend`, `audio_ms`, `wall_ms`, `fixture_sha`, `harness_cpu_pct`, `harness_warning`, `gpu_workload_proof`, `token_coverage` (the scenario's `token-coverage.json`: `capture` as `rig` or `mock`, `expected`, `found`, `missing`, every token with its verdict, the speakers, `md_names_found`) and `forced_cpu`. `--record` files the same figures as the `meetings` block of the latest checked-in benchmark report for the host and tier under [docs/reports/benchmarks/](reports/benchmarks/README.md), written in place so the file keeps the benchmark's own date and commit while the block carries the pack's, and re-renders the README table through the benchmark writer, which is how the report is checked in per release ([docs/RELEASING.md](RELEASING.md)). Under CI the drive job runs the pack after the GUI pack with the mock fixtures, `tiny.en` and the cached diarization set; there the figures are recorded and never gated, the rig capture step and the GPU proof are the allowed skips the blockers name.

## Drivers

On Hyprland, `keyboard_only` reads the compositor monitor state before launching the app and retains `keyboard-desktop.json`. A locked session or unreadable lock state fails explicitly. Unlock the native desktop before running the drive; `loginctl LockedHint` alone does not reflect Quickshell’s session lock. Private Xvfb sessions remain independent of that native lock.

The private Xvfb session uses foreground CUA input inside that isolated desktop, which preserves Return and text selection on Qt fields. Ordinary desktop runs retain CUA's background default. For a coordinated native keyboard-focus verification, set `CUA_DRIVER_DELIVERY_MODE=foreground` on the QA process and keep other desktop input paused for the run; CUA restores the prior active window after each foreground action. Missing container geometry is supplemented from an unambiguous native accessibility match while preserving CUA's action tokens. A vanished object during an AT-SPI tree walk permits one immediate fresh whole-tree read. A second failure is reported; permanent errors are never retried. Partial trees are never returned.

Scenarios are written against one interface (`dettivo_qa::driver::Driver`): launch, find an element by accessible name, click, type, read a value, wait for a label, screenshot. Two implementations exist and every scenario runs on both; a scenario that drives through the compositor and the socket alone (`hotkeys_hyprland`) declares that it needs no driver, and a scenario's own preflight can skip it with the reason (a missing tool, session or device):

| Driver | How | When |
|---|---|---|
| `cua` | `cua-driver serve` on a private socket plus `cua-driver call`; AT-SPI for elements, XTEST for input. Pinned per release (`scripts/qa/install-cua-driver.sh`). | Desktop drives on the development machine and in CI. |
| `atspi` | In-repo: the `atspi` crate over the accessibility bus for elements, `x11rb` XTEST for input and `GetImage` for screenshots. Depends on nothing outside the repository. | The fallback; the weekly CI job runs the whole pack on it. |

The AT-SPI driver acknowledges focus before returning from a click on an editable, enabled, focusable text field. It requires the field's current `Focused` state and the launched application's active X11 window within two seconds. Buttons and disabled, read-only or nonfocusable controls retain ordinary click behavior. Text values are read directly from the owned application's target object, so unrelated list delegate churn cannot invalidate a stable field read. History submits only after observing the complete query; read failures or a driver returning only the field name cannot verify delivery.

A scenario file may not name a driver implementation; `dettivo-qa lint-scenarios` fails on `CuaDriver`, `AtspiDriver`, `cua-driver` or `atspi::` inside `crates/dettivo-qa/src/scenarios/`.

QA profiles isolate `CODEX_HOME` and `CLAUDE_CONFIG_DIR` along with HOME and the XDG configuration, state, data and cache locations. Profile-backed commands clear the inherited environment and forward only selected desktop, accessibility and audio connection variables before applying deliberate scenario overrides. Inherited `DETTIVO_CONFIG` and `DETTIVO_DATA_DIR` cannot redirect a drive into the user's files (ADR 0050).

A named configuration path editor may expose its exact absolute path value; its label, diagnostic text and unrelated values remain subject to the negative-text checks. This keeps file editing testable without exempting whole routes or developer messages.

## Benchmarks

`dettivo-qa bench` (`just bench`, [ADR 0029](adr/0029-nfr-calibration-and-the-benchmark-suite.md)) turns the numbers the product promises into a checked-in report: one JSON per host and tier under [docs/reports/benchmarks/](reports/benchmarks/README.md), every figure beside the calibrated target it is held to, rendered into that directory's README. A release runs it on the development machine and commits the report ([docs/RELEASING.md](RELEASING.md)); CI runs `just bench-quick` (three iterations, the CPU, the report uploaded as the `bench-quick` artifact) so the suite is proven on every push while a runner's numbers gate nothing.

```
just bench target/vulkan/debug   # the GPU tier with the Vulkan engines, filed under docs/reports/benchmarks
just bench-cpu target/vulkan/debug   # the CPU tier on the same machine (DETTIVO_FORCE_CPU=1), filed beside it
just bench-quick                          # three iterations on the CPU under qa-evidence/ (CI)
dettivo-qa bench [--cpu] [--quick] [--step <name>] [--engines <dir>] [--out <dir>] [--json]
```

The tier is the daemon's `system.capabilities.platform.tier`: `gpu` when a Vulkan device is installed and no loaded engine fell back to the CPU, `cpu` otherwise or under `--cpu`, with the reason recorded. `--engines <dir>` names the engine binaries to measure (`just build-whisper-vulkan`, `build-parakeet-vulkan` and `build-llm-vulkan` into one target directory for the GPU tier; the workspace build is the CPU engines). Each step measures the product's default model when it is on disk (`large-v3-turbo`, `parakeet-v3`, `qwen3-4b-instruct-2507`) and the test model otherwise; a missing model skips the row naming the download command, never failing the suite. Every timed step records its iteration count and every sample with p50, p95, min and max, so a bad run is visible rather than averaged away, and each bench daemon's stderr lands beside the report under `qa-evidence/<run>/bench/<step>-daemon.log` so a failed step can be read back.

| Step | What runs | Held against |
|---|---|---|
| `first_insert` | The dictation pack's timing scenario without a window: for Whisper and Parakeet, a daemon in a bench profile dictates the 11 s fixture through the mock microphone once cold and ten times warm (three under `--quick`); each run measures the stop request to the completion event and splits it with the event's `timings` block. The insert leg goes through the mock inserter, so the figure is the engine tier's; the pack's `first_insert_timing` measures the real chain. A row carries a figure only when every warm run completed; fewer completed runs fail the step with the count and the failures, and the partial spread stays in the JSON beside them without becoming the headline. | NFR-1 (GPU) or NFR-2 (CPU), the p50 of the tier's engine (Whisper large-v3-turbo on the GPU tier, Parakeet on the CPU tier, ADR 0029); every row carries its own figure and verdict and the README lists them beneath the headline |
| `stt_throughput` | The clip repeated into five minutes of audio (one minute under `--quick`), transcribed once by each speech engine's CLI mode; the realtime factor is audio over wall time with the model load included, and a warm-up over the clip alone records what the load costs. | NFR-4 (GPU) or NFR-5 (CPU), the tier's engine's row (Whisper on the GPU tier, Parakeet on the CPU tier); every row carries its own verdict |
| `llm_rewrite` | The Polish goldens' inputs (`crates/dettivo-language/tests/goldens/polish_fallback.json`, three under `--quick`) through `dettivo-engine-llm --prompt` with a fixed rewrite system prompt, one process each: the latency spread, the tokens, and tokens per second past a load-only run. | recorded; no NFR names a rewrite budget beyond `[llm] timeout_ms` |

## Speaker accuracy

`just diar-bench` scores the speaker pass on AMI dev and your retained English and German meetings in under a minute, from cached engine outputs, through the product's own Rust assignment rule. The hill-climbing loop is to save a baseline (`just diar-bench --save before`), change the rule in `crates/dettivo-meeting` or add a variant, and rerun with `just diar-bench --baseline before` to read each metric's delta with a 95% interval. The headline is the attribution error, the share of reference words whose line did not get the right speaker, with an unlabelled line counting as wrong. Its parts sit beside it: wrong and unlabelled words, DER split into missed, false alarm and confusion, short-turn error, the local/remote proxy for meetings nobody labelled, and engine speed. Tune on AMI dev, and report AMI test (`--heldout`) once, without retuning on it. [The diarization bench](diarization-bench.md) defines every metric and split, shows how to add a variant, and lists the labels format and the first-time setup (`just diar-bench-setup`).

## Engine pipelines

`dettivo-qa pipeline import-merge` (`just qa-import-merge`, ADR 0022) proves the chunked import pipeline against the real engine: it writes the jfk clip four times with a second of silence between takes, cuts it with the pipeline's chunker at 16 s windows, 2 s overlap and a 5 s margin (every cut lands in a gap and every chunk after the first starts inside a take, so the seam rules run), transcribes each chunk through `dettivo-engine-whisper` in CLI mode with tiny.en, merges the overlaps, and passes when the merged text holds all four takes exactly once (none lost at a cut, none duplicated across an overlap) with a word error rate under 0.10 against `crates/dettivo-qa/fixtures/import-merge/golden.txt`. The report (`import-merge-report.json`: the chunks with their cuts and texts, the merged text, the takes found, the rate, the verdict) and the chunk files land under `qa-evidence/<run>/import-merge/`; without the model or the clip it reports `skipped`. The CI `drive` job runs it after the contract replay.

`dettivo-qa pipeline diarization` (`just qa-diarization`, ADR 0035) proves the diarization engine against the two-speaker fixture: `crates/dettivo-qa/fixtures/diarization/two-speakers.wav` is two Piper voices taking six turns with one overlap (synthesised through sherpa-onnx's offline TTS by `scripts/qa/make-diarization-fixture.py`, the expected turns beside it in `two-speakers.turns.json`), the engine's CLI mode diarizes it with the speaker count given, and the answer is scored by diarization error rate (missed speech, false alarm and confusion over the reference speech, every 10 ms, under the speaker mapping that minimises it); the pipeline passes under 0.20 with exactly two speakers, `--bench` records the realtime factor and holds it to NFR-4's four times real time, and `diarization-report.json` (the turns, the rate and its parts, `backend`, optional `fallback_reason`, the timing and the verdict) lands under `qa-evidence/<run>/diarization/`. Without the model set (`scripts/models/fetch-diarization-model.sh`) it reports `skipped`; CI runs it after the import merge with the cached set.

On CUDA, `--bench` also runs the same binary, model and WAV with `--provider cpu`. `cpu_comparison` records `elapsed_ms`, `realtime_factor`, `error_rate`, `found_speakers` and `speedup`; the gate requires matching CPU/CUDA DER and speaker count and at least 4x CPU throughput, in addition to the realtime floor. The report names both figures when they differ. `backend` is null only when skipped. The meetings pack samples the diarization process into `diarization_throughput/gpu-samples.json` and copies those samples to `gpu_workload_proof/diarization-gpu-samples.json`; CUDA proof requires the recorded diarization PID itself. CPU runs do not need that CUDA proof.

`dettivo-qa pipeline parakeet-alignment` is the S-13 spike (ADR 0018): it runs `dettivo-engine-whisper` and `dettivo-engine-parakeet` in CLI mode over the jfk fixture, pairs every word Parakeet returns with the golden word alignment checked in at `crates/dettivo-qa/fixtures/alignment/jfk.words.json` (a wav2vec2 CTC forced alignment, built once and recorded in the file), and writes `alignment-report.json` with the median and p95 word offsets, the segment boundary error of both engines, the backend each engine ran on and why, and the verdict under the rule the report states before any number: `meeting_capable` when every Parakeet model measured pairs at least 90 % of the golden words with a pooled start/end p95 within 200 ms and a median within 100 ms, `dictation_only` otherwise, `undecided` when the fixture, an engine or a model is unavailable. `--cpu` pins both engines to the CPU, `--report <file>` also writes the checked-in copy (`docs/reports/parakeet-alignment-report.json`), and the evidence copy lands under `qa-evidence/<run>/parakeet-alignment/`.

## Contract replay

`dettivo-qa contract` and the release gate share one complete MCP, REST and socket replay. Required transport result sections must be nonempty and valid. ## Visual regression

Every surface can be compared with an approved picture on every theme and scale, so a control that drifts from the design, a stock widget that leaks in or a font that falls back shows up in a report (ADR 0021). The comparison is optional: it gates neither CI nor the release (ADR 0066). `just qa-visual` (`dettivo-qa visual`) reads `qa/visual/manifest.toml`, renders every surface it lists at 1x and 2x on the three theme fixtures under `qt/fixtures/themes/` (`black-gold`, the artboards' theme; `catppuccin-latte`, light; `tokyo-night`) and on the two built-in palettes (`builtin-dark`, `builtin-light`, the portal colour scheme pinned with `DETTIVO_COLOR_SCHEME`), diffs each render against its baseline with `dettivo-visual-diff` (an artboard crop by structure alone, since the artboard is drawn in one theme; an approved render of the same theme and scale strictly as well, the same dimensions and each pixel's normalized RMS RGB distance within the surface's `colour_tolerance`, 0.06 by default; its structural artboard score is advisory), and exits 1 on any entry that is not a pass. The CI job `visual` runs it and blocks the merge; the canary runs after it.

The report lands under `qa-evidence/visual/` as `visual-report.json` and `visual-report.md`, one row per entry with the score, the threshold, the advisory score against the artboard crop on every theme, and links to the render and the diff image (baseline, render and the cell heat map stacked).

## Frame pacing

Every Qt host carries the pacing collector (`qt/host/pacing`): `DETTIVO_QA_PACING=<file>` makes it record every swapped frame's timestamp and every render's duration on the render thread and write the summary into the file once a second and as the process quits (frames, the refresh rate, dropped frames with their timestamps, render cost mean, p99 and max, the swap list, every theme change with the moment it applied and the delay to the next swapped frame, the `surface`). The drives copy the summary into their evidence as `pacing-<surface>.json` with the `scenario` and a `verdict`. `dettivo-osd --pacing <seconds>` (`just qa-osd-pacing`) is the same collector over a fixed run on the real display.

The verdict judges dropped frames only while the surface animates (the pill's bars from Listening to the stop; a static app window is idle, not dropping) and at the slower of the display's refresh rate and 144 Hz, the fastest rate NFR-12 names, so a 240 Hz desktop is not failed on a hitch no named rate would show; the budget is two dropped frames per thousand animated frames with a floor of two, the render cost at the 99th percentile stays under a millisecond once a hundred frames have rendered, and a theme switch applies within 100 ms. On this desktop the thresholds gate; under CI (the `CI` variable set) the numbers are recorded and the presence of the report is the gate, because Xvfb has no real refresh.

## Desktop memory reference runs

The Thor app-process limits are RSS ≤320 MiB (327,680 KiB) and anonymous memory ≤128 MiB (131,072 KiB). Each exact limit passes; one KiB above either fails. PSS has no enforced cap. RSS includes shared libraries and graphics mappings; PSS apportions shared pages; anonymous memory includes Qt and driver allocations as well as Dettivo's. Daemon and engine processes are excluded from these app budgets.

Build Release Qt and release-profile Rust companions with `just build-release build-qt`, then run these from the repository root. Each command launches the app five times, so no external repetition loop is needed:

```sh
DETTIVO_BUILD_PROFILE=release target/release/dettivo-qa drive app_memory.wayland --evidence qa-evidence/memory-wayland
scripts/qa/xvfb-session.sh env DETTIVO_BUILD_PROFILE=release target/release/dettivo-qa drive app_memory.xvfb --evidence qa-evidence/memory-xvfb
```

Run the Wayland command in Thor's native session. This scenario overrides the ordinary drives' XWayland platform selection and resolves the caller's Wayland socket to an absolute path before isolating the profile. It uses Hyprland's one-shot `exec_cmd` float/size effects to launch only its private app window at 1280×820 logical pixels, retaining the compositor's actual scale. The probe records the app PID separately from the short-lived launcher and checks process identity before cleanup. No persistent compositor rule is installed. Run the Xvfb command in the private desktop provided by the wrapper; select an unused `XVFB_DISPLAY_NUMBER` when its default `99` is occupied. An unavailable compositor, missing release binary or unsupported environment is an explicit failure or blocker; a failed measurement never counts as a successful zero.

The first-frame clock starts at app entry and captures the first swap on the render thread. GUI event delivery and journal-writing delay do not extend that timestamp. Earlier reports retain their original queued-delivery measurements.

Each fresh launch opens Home with the same fixture data and waits for a connected daemon, then samples after five seconds idle without capture, playback, download or analysis. Keep the reference window, scale and theme equivalent across launches. `startup.json` in each scenario's driver directory carries individual samples and maxima, raw KiB and converted MiB, the limits and per-metric outcomes. Each `launch-N/` retains process status, `smaps_rollup`, the app journal, stdout/stderr and status metadata. Recorded context includes process identity, Release build configuration, renderer, actual platform and runtime, window dimensions, scale, theme and measurement timing.

Every launch must pass both memory limits. Missing, malformed, unreadable or partial metrics and an app that exits before sampling fail the measurement. Preserve failed samples and compare equivalent profiles before attributing changes to application code. These budgets are engineering allowances on Thor; recalibrating them frees no memory. The original fn-17 requirement and fn-54 failure remain historical records, as explained in [ADR 0059](adr/0059-desktop-memory-budgets-follow-measured-reference-profiles.md).

First frame remains under 300 ms. Measure the real theme swap separately with `app_theme_live`, retaining the under-100 ms requirement:

```sh
scripts/qa/xvfb-session.sh env DETTIVO_BUILD_PROFILE=release DETTIVO_TIMING_GATE=1 target/release/dettivo-qa drive app_theme_live --evidence qa-evidence/memory-theme
```

## Lints

`just lint-qml` runs the copy lint (`scripts/lint-copy.sh`, ADR 0042): every `qsTr` string in the module and the apps is sentence case with a full stop when it is a sentence, carries no exclamation mark, ellipsis, `Please`, `Oops` or `Error:` prefix, and a string the pill shows (`components/Osd*.qml`) is one sentence; a quoted name is exempt through a `//: verbatim` marker on its line, and `--self-test` plants three bad strings and proves each is named by file, line and rule.
