# Installing

One command puts Dettivo for Linux on an Omarchy or Arch machine, and one more enables it in your session. Nothing here needs a GPU: the engines run on Vulkan when a device is installed and on the CPU otherwise, and models download on first run ([docs/models.md](models.md)).

## From the AUR

```
yay -S dettivo-bin                              # the release build, ready in a minute
systemctl --user enable --now dettivod.socket   # the daemon starts on the first request
dettivo setup omarchy                           # the bindings, the bar plugin and the pill on Omarchy
dettivo setup hyprland                          # the bindings on plain Hyprland (sway and niri likewise)
dettivo doctor                                  # what is installed, what is missing, which tier this machine is
```

`dettivo-bin` repackages the release tarball published on GitHub and verifies it against the `SHA256SUMS` published beside it. `dettivo` builds the same tree from the tagged source with `just package`, which takes the Rust toolchain, CMake, Qt 6, the Vulkan headers and shaderc and around twenty minutes; both install the same files and the same `dettivo.install` message. The packages depend on Qt 6 (base, declarative, svg, wayland), layer-shell-qt, tomlplusplus, wayland, libxkbcommon, PipeWire and the Vulkan loader; a Vulkan driver for your GPU is optional and turns the engines to the GPU tier ([ADR 0029](adr/0029-nfr-calibration-and-the-benchmark-suite.md)).

The systemd preset enables `dettivod.socket` and `dettivo-osd.service` for sessions created after the install; an existing session runs the `enable --now` line once. On Omarchy the bar plugin hosts the pill and `dettivo-osd.service` exits with a notice, so one pill shows ([docs/osd.md](osd.md)).

## Optional NVIDIA diarization

The `dettivo-engines-cuda` recipe under `packaging/aur/` builds a drop-in for the post-meeting speaker pass. It depends on Dettivo, CUDA 13 and cuDNN 9. The default package keeps CPU diarization and Vulkan speech recognition and language models; AMD and Intel machines keep that default.

With the drop-in installed, `[engines.diarize] backend = "auto"` selects CUDA when its prerequisite checks pass and falls back to CPU with the reason when they fail. Later model initialization failures and GPU out-of-memory errors do not trigger this fallback. `cuda` requires a working CUDA provider; `cpu` forces CPU. Settings / Models edits this key. `dettivo doctor` and `dettivo speech engines` name the engine path and the backend of its last load. Removing the drop-in returns subsequent engine starts to the CPU package when no explicit engine-directory override is set. Stop active meetings before replacing engine packages, and restart the daemon afterwards to use the new binaries.

## What lands where

| Path | What |
|---|---|
| `/usr/bin/dettivod`, `dettivo`, `dettivo-mcp`, `dettivo-qa` | The daemon, the command line, the MCP server and the QA runner |
| `/usr/bin/dettivo-app`, `dettivo-osd`, `dettivo-sheet`, `dettivo-insert-target`, `dettivo-bar` | The app, the recording pill, the sheet, the insertion target the QA rig drives and the bar render host the visual QA drives |
| `/usr/lib/dettivo/engines/dettivo-engine-{whisper,parakeet,llm,diarize}` | The three ggml engines with Vulkan and CPU fallback, plus CPU diarization |
| `/usr/lib/dettivo/engines-cuda/` | Optional `dettivo-engines-cuda` diarization engine and ONNX Runtime provider libraries; an engine here wins over the default |
| `/usr/lib/dettivo/qml/Dettivo`, `DettivoStyle` | The shared QML module and the control style, with their `qmldir` and `qmltypes` |
| `/usr/share/dettivo/omarchy/` | The Omarchy bar plugin `dettivo setup omarchy` installs into the shell |
| `/usr/lib/systemd/user/dettivod.socket`, `dettivod.service`, `dettivo-osd.service` | The user units; `/usr/lib/systemd/user-preset/90-dettivo.preset` enables them |
| `/usr/share/applications/dettivo.desktop` | The launcher entry with its History and Meetings actions |
| `/usr/share/icons/hicolor/scalable/apps/dettivo.svg` and the 16, 32, 64 and 128 px PNGs | The six-bar mark |
| `/usr/share/bash-completion/completions/dettivo`, `/usr/share/zsh/site-functions/_dettivo`, `/usr/share/fish/vendor_completions.d/dettivo.fish` | Completions generated by `dettivo completions <shell>` from the binary that ships |
| `/usr/share/licenses/dettivo/LICENSE`, `/usr/share/licenses/dettivo-bin/LICENSE`, `/usr/share/doc/dettivo/NOTICE.md` | The licence and every vendored component with its licence |

`packaging/manifest.txt` is this list as the package build and the install test check it; models are never in it.

## How the daemon finds an engine

The daemon looks for `dettivo-engine-<name>` in this order and stops at the first file it finds:

1. `[engines] directory` in `config.toml`, when set ([docs/config.md](config.md)).
2. `/usr/lib/dettivo/engines-cuda`, the optional CUDA diarization drop-in.
3. `/usr/lib/dettivo/engines`, where the package installs the engines.
4. The directory of the running `dettivod` binary (a development checkout).
5. Every `PATH` entry.

`dettivo speech engines` and `dettivo doctor` report the directory that answered for each engine beside the backend of its last load, so a stray build on `PATH` or a CUDA drop-in is visible rather than guessed at. `DETTIVO_FORCE_CPU=1` keeps every engine on the CPU whichever directory it came from.

## Building the package yourself

```
just package                # dist/dettivo-<version>-linux-x86_64.tar.zst and SHA256SUMS, checked against the manifest
scripts/package.sh --cuda   # the CUDA diarization-only tree and its separate manifest
just package-bin            # the dettivo-bin package from that tarball, with required namcap validation
just package-bin build/dist # stage and package from the same optional destination
just package-source         # the dettivo package from an archive of this tree (the full release build)
just install-test           # unpack the package under build/install-root and run every check
```

`just package` builds every crate in release mode with the three ggml engines on Vulkan and the diarization engine with the sherpa-onnx and ONNX Runtime libraries beside it under `usr/lib/dettivo/engines` ([ADR 0035](adr/0035-sherpa-onnx-diarization-engine-and-the-speaker-pass.md)), installs the Qt binaries and the module through CMake with `/usr` as the prefix, adds the units, the desktop entry, the icons, the completions, the licence and `NOTICE.md`, and refuses a tree that differs from `packaging/manifest.txt`. `DETTIVO_PACKAGE_CPU_ONLY=1` builds the engines without Vulkan on a machine without the headers; it is never a release build. `CMAKE_PREFIX_PATH` pointing at unpacked Vulkan-Headers and SPIRV-Headers installs works where the system headers are absent ([docs/engines.md](engines.md)).

`just install-test` runs [`scripts/packaging/install-test.sh`](../scripts/packaging/install-test.sh) against the built package under a prefix, so it touches nothing outside `build/`: the file list, the desktop entry and the units, `dettivo --version`, the completions loading in bash, zsh and fish, Home rendered from the installed module on the offscreen platform, every engine's help, the CPU-fallback smoke (each engine's command line mode on tiny.en, Parakeet v2 and Qwen3 1.7B under `DETTIVO_FORCE_CPU=1`, every result's backend `cpu`) and one dictation of the fixture through the installed daemon with the mock microphone, timed from the completion event against NFR-2. `build/install-test.json` names every step with its outcome, detail and exit code. CI runs the same script on a clean container after `pacman -U`, which proves the runtime path and the import path the binaries carry; `scripts/packaging/install-test.sh --session <package>` on a fresh virtual machine adds the real units, socket activation under 300 ms, `dettivo setup` and the pill's service ([docs/RELEASING.md](RELEASING.md)).

The recipes live under [`packaging/aur/`](../packaging/aur/); `scripts/packaging/lint.sh` (part of `just lint`) keeps their `pkgver` at `Cargo.toml`'s version, their `.SRCINFO` in step with `makepkg --printsrcinfo`, the two install scripts identical, the desktop entry valid and the changelog section present. `packaging/aur/publish.sh <version>` pushes both recipes to the AUR by hand once the GitHub release exists ([ADR 0034](adr/0034-install-layout-cuda-drop-in-and-release-workflow.md)).
