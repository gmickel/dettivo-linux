# 0032. A private polish fine-tune sideloads from the macOS manifest, every candidate is scored by the macOS harness through the Linux engine, and promotion stays a config change

Status: Accepted 2026-09-05

## What this gives you

The dictation fine-tune the macOS pipeline trains runs on Linux the day it is exported: one script turns the fused export or the LoRA adapter into a GGUF beside a `current.json` in the macOS shape, `dettivo llm experiment use` points Enhanced at it, and the catalogue default stays exactly where it was until you say otherwise. Whether it earns its place is measured, not asserted: `dettivo-qa polish-eval` runs a held-out set through the daemon's own Enhanced pipeline against the local engine, scores it with the macOS metrics, checks the macOS hard gates and the relative gates against an incumbent, and writes a report that carries figures and row ids, never a row's text. The same command on the twelve-row sample with the recorded rewrites is a CI gate on the harness itself.

## Situation

ADR 0023 ported the Polish layers with their goldens and ADR 0026 put the four catalogue Qwen3 GGUFs behind the local engine. What remained of the masterplan's parity principle (FR-M9 to FR-M11, Principle 14: same models, same bar) were the parts that make quality comparable rather than claimed: the private fine-tune, which on macOS loads from `models/polish-experiments/current.json` and never from a catalogue, and the evaluation harness (`bench_dataset.py`, `score_results.py`, `check_promotion.py`, the promotion targets and the held-out JSONL sets) that decides on macOS whether a challenger replaces an incumbent.

Three things had to be settled. Where a fine-tune lives on Linux and in which form: the macOS export is an MLX-fused Hugging Face checkpoint, and llama.cpp reads GGUF, either fused or as a LoRA adapter over a base it already has. What the eval measures: the engine's raw answer is cheap to score but is not what a user sees, since the guards, the repair pass and the fallback decide what is inserted. And what promotion means on Linux: the macOS rule is optional first, the 4B runtime stays default, and a challenger is promoted only after clearing the hard gates on the same held-out sets, measured through the runtime that ships.

Two smaller questions came with them. Which llama.cpp converts the file: a converter newer than the engine's reader writes tensors and metadata the engine cannot load. And where a dictionary-correction eval sits, since `dettivo-qa` reaches the daemon through `dettivo-proto` only and cannot link the language crate.

## Decision

A fine-tune is a sideload. `[llm] polish_experiment` names a manifest under `[llm] experiments_dir` (`<models>/polish-experiments` by default); `current` reads `current.json`, the macOS shape (`id`, `displayName`, `relativeModelPath`) with two optional Linux fields, `format` (`gguf`, the default, or `gguf-lora`) and `baseModel` (a catalogue id, required for an adapter). `dettivo_speech::llm::sideload::resolve` turns the manifest into the one `.gguf` its directory holds, refusing a path that leaves the experiments directory, a directory with none or two, and an adapter without a base, each with a message that names the file at fault. The daemon's `LocalLlm` binds the result: a fused GGUF replaces the catalogue file, an adapter loads over its base through the engine protocol's new `load.lora` field (the engine initialises the adapter once and sets it on every context; the supervisor reloads when the adapter changes and reports it), and a manifest that does not resolve leaves Enhanced on `[llm] model` with the error kept. `llm.models.status` lists the sideload as one more row, `source = "sideload"`, with `format`, `base_model`, the selection mark and `manifest_error` when there is one, and the result carries `polish_experiment`; `llm.engine.status` reports `lora`. The catalogue methods never know the id: `download`, `cancel` and `delete` answer `NOT_FOUND` naming the catalogue's ids, and nothing is ever offered for download (decision D14 stands). `dettivo llm experiment status|use|clear` and a `dettivo doctor` line are the surfaces.

The conversion is `scripts/models/convert-polish-finetune.sh`, which pins llama.cpp at the revision `llama-cpp-2 0.1.156` vendors (`e79e4bf660e19f2ad851e06c6913f7a8c5852621`) and runs its `convert_hf_to_gguf.py` (a fused export, to F16, then `llama-quantize` to Q4_K_M, the catalogue footprint) or `convert_lora_to_gguf.py` (a PEFT adapter, with its Hugging Face base), writes the SHA-256 and the manifest, and with `--verify` loads the result in the engine's CLI mode. Every step is named and a converter or quantiser exit code stops the script naming the step. `--dry-run` validates the toolchain and the paths, and CI runs it against a placeholder export (`just polish-convert-check`).

The harness is `dettivo-qa polish-eval` (`crates/dettivo-qa/src/polish_eval/`). `dataset` reads the macOS canonical rows with the spec's names as aliases. `runner` starts a daemon in an isolated profile the way `contract` does, with `[llm] provider = "local"` and the candidate (a catalogue id, its files hard-linked from the machine's model directory rather than the directory itself; `sideload[:<name>]`, the experiments directory read where it is; a GGUF path, wrapped in a manifest of its own; `fixture:<dir>` or `echo` for a run without a model), and drives every row through `polish.test { mode: enhanced, preset, style, bundle_id }`, so the prompt profile, the guards, the repair pass and the fallback are the product's. `scorer` is `score_results.py` case for case (the ten metrics under their macOS names, the cuts by preset and language, the Python percentile and median), `gate` is `check_promotion.py` with the macOS targets checked in as `qa/polish-eval/targets.json` and one Linux rule on top: the relative gates compare only two reports from the same backend. `--engine-only` runs the rows through `dettivo-engine-llm --prompt --raw` for the tokens-per-second figure without the guards. The report (`docs/reports/polish-eval/<date>-<model>-<set>.json`) carries the metrics, the model id with its file and SHA-256, the backend, the engine version, the git sha, the row count and ids, the gate stated per metric and the comparison with `macos-baseline.json`; `README.md` beside it is regenerated on every run. A test scans the directory for row text on every run.

The dictionary-correction eval lives with the layer it measures: `crates/dettivo-language/tests/dictionary_eval.rs` scores the twenty public rows of the macOS `eval-v1.jsonl` through `dettivo_language::raw` and holds the figures to `docs/reports/polish-eval/dictionary-eval-v1.json`, which records them beside the macOS `exact` and `hybrid` strategies and names every row that differs.

Promotion is a config change. A candidate that clears every gate is not promoted by code: `[llm] polish_experiment` is set on the machines that opt in, the report is the record, and the catalogue default does not move. The stop rule in the targets file is the macOS one: the confirmed 1.7B incumbent stays frozen until a challenger repeat-confirms a win.

## Consequences

`llm.models.status` rows gain `source`, `format`, `base_model` and `manifest_error`, its result `polish_experiment`, and `llm.engine.status` gains `lora`, all registered in `docs/api/linux-deltas.md` with the fixtures updated; `[llm] polish_experiment` and `[llm] experiments_dir` are in `config.toml`, `config print-default` and `docs/config.md`. The engine protocol's `load` gains `lora` (`docs/engines.md`), and the speech engines ignore it. `docs/polish-models.md` is the runbook: the conversion, the manifest, the opt-in key, the eval command and how to read a report.

The sideload resolver is unit-tested against the macOS manifest shape and both Linux forms; `crates/dettivod/tests/llm_sideload.rs` proves the daemon side against a live daemon, and with the Qwen3 1.7B file on the machine standing in for the fine-tune, that a `polish.test` in `enhanced` mode names the sideload. The scorer and the gate are unit-tested with one passing and one failing row per macOS metric and the gate's three outcomes. `crates/dettivo-qa/tests/polish_eval.rs` runs the sample set with the recorded rewrites against `golden.json`, checks that an unknown preset fails naming the row, and scans the checked-in reports.

On the development machine (RTX 4090, Vulkan) the two private held-out sets ran through `qwen3-4b-instruct-2507` and through a Qwen3 1.7B converted by the runbook from its public Hugging Face checkpoint and installed as `current`, the private weights being on the macOS machine and one `scp` plus the same script away; the four reports under `docs/reports/polish-eval/` state every hard gate. The comparison with macOS reads `macos-baseline.json`, whose figures are the repeat-confirmation medians the macOS research notes record for the bootstrap held-out set; the private sets have no summary checked in on macOS, so the quality rows compare against those figures and the latency rows are informational, a different runtime on different silicon.

Bounds: the held-out runs recorded here predate the raw layer's protected tokens (ADR 0023, `[dictation] protect_tokens`), so they surface protected-token failures (`src/app/index.ts` reaching the model as `index. Ts`) that the raw layer has since removed; the next runs measure the model alone. The dictionary eval records a gap rather than parity: Linux has no dictionary corrector, whole-word replacement is the nearest thing and it over-applies to common words (a URL is protected on both sides); the macOS `hybrid` strategy is the bar and its port is a spec of its own. A LoRA adapter is proven at the resolver, the engine and the daemon level with a placeholder; converting a real adapter needs the PEFT export the macOS pipeline can produce.
