# 0033. Settings offers everyday controls and advanced access to one configuration file

Status: Accepted 2026-09-05

## What this gives you

Settings offers everyday controls first and the full configuration behind a shared Advanced toggle. Nine sections edit the same file through the daemon. Labeled choices, individual Polish transforms, a Vocabulary editor and per-setting reset actions make the common workflow discoverable. The file remains available through Open in editor and a shipped, commented reference.

## Release UX amendment, 2026-09-15

Simple/Advanced is session-local presentation state. Toggling it never changes configuration. Technical rows, generated snippets, raw previews, agent connection facts and experimental models appear in Advanced mode. Setup actions remain visible. Deep links to a key reveal Advanced mode before scrolling to its control.

Reset uses `config.unset` and the daemon's key registry defaults. The dictation provider/model pair resets atomically through the existing selection API. Unknown menu values remain explicit and unchanged. Vocabulary writes a typed array of whole terms. Transform switches retain additional configured values. All writes retain validation, comment preservation, environment locks and file-refresh behavior.

History copies the displayed transcript with a paste instruction. Its previous action called `insert.perform` while Dettivo held focus, and the insertion guard rejects Dettivo's app IDs with `target_is_self`. No reliable focus-restoration contract exists for this action. The clipboard workflow leaves insertion history unchanged; the global reinsert shortcut remains available from the destination app.

The remaining sections record the original implementation decision. This amendment supersedes the always-visible previews, eight-section navigation and artboard layout descriptions below. Visual baselines need separate human approval for the changed layout.

## Situation

The masterplan fixes Settings as a face over the file (FR-C3, FR-C6): writes preserve comments and ordering, every route shows the keys it edits and offers to open the file, and the file stays hand-maintainable. The daemon already served `config.get|set|unset|validate|path` with `toml_edit` behind them (ADR 0009), the app shell had eight settings sub-routes as scaffolds naming their keys (ADR 0020), first run had shown how a screen writes configuration through the daemon (ADR 0024), and three artboards were approved (`settings-models.png`, `settings-hotkeys.png`, `agents.png`). Three things were missing. The app had no way to describe a key: its type, its default and its sentence lived in the Rust schema and the default file's comments, so a row would have carried a second copy of every description. Nothing told the app when the file changed under it, so a CLI write and an open route would have drifted until a reload. And two writers could edit the file at once: `config.set` read the text, changed it and wrote it back without a lock, so a write from the app and an `unset` from the command line could interleave and bring a removed key back.

## Decision

- **One key registry, served by the daemon.** `config.keys` answers every leaf key of the schema with its section, its kind (`text`, `integer`, `float`, `boolean`, `list`, `table`), its default and the sentence the default file carries above it, read from the comments of `DEFAULT_TOML` at run time, so the file, `dettivo config keys` and the app describe a key with the same words. The app's `SettingsModel` reads the registry once per connection and hands every row its sentence, its kind and its default; nothing in QML repeats a description.
- **The routes' keys are one table, compiled in and read by three consumers.** `qt/host/app/settings_keys.cpp` lists, between markers, every key each section edits in row order and, separately, the keys no route edits with the reason (`polish.rules`, `polish.apps` and `polish.presets`, tables of tables that `dettivo polish` and the file edit). The "This route writes" block reads it, the round-trip drive reads it to know what to edit, and `scripts/lint-settings-keys.sh` holds it against the `config.keys` fixture and against docs/config.md's "Keys by route": a schema key with no editor and no reason, a route key the schema lacks, or a key the documentation does not place fails the lint by name.
- **Writes go through the daemon, one at a time.** A control commits once (a field on Enter or when the focus leaves it with a changed text, a switch on click, a choice on pick) and sends `config.set`; the daemon coerces the string to the key's type, validates, writes with comments kept and reloads. A refusal comes back with the key in `details.key` and shows under the control; the file is untouched. The daemon now holds one lock across every read-modify-write of the file (`config.set`, `config.unset`, `speech.selection.set`, `llm.endpoints.trust`, the Polish rule and app writes), so two connections cannot lose each other's change.
- **The file is the truth and the route follows it.** The daemon publishes `config.changed` (`path`, `ok`, `keys`) on every reload, whether a `config.set` or the watcher's hand-edit caused it; the settings model refreshes its values and says so under the title (`The file changed on disk; 1 value(s) refreshed.`). A field being edited keeps the edit and says what the file now holds; a field that is not being edited follows the file. A key the environment sets (`DETTIVO_IPC_SOCKET`, `DETTIVO_DATA_DIR`, `DETTIVO_QA`) shows the `env · VARIABLE` chip and its control is disabled.
- **Every section shows what it writes and where.** The column names the file and opens it in the desktop's editor (`xdg-open` through `QDesktopServices`); every page ends with the "This route writes" block, the keys it edits as TOML with the values in force, one line per table. `dettivo app open settings.<section> --id <key>` scrolls the row that edits a key into view, which is also how the drive reaches every row.
- **Agents and Diagnostics run the command line rather than copy it.** The Agents route shows the socket facts, the REST shim's facts, the four MCP hosts with the file each reads and whether Dettivo's entry is in it, and writes a host through `dettivo mcp config --host <id> --write`, the one code path that writes host files; the app runs the command from home so a project-scoped host file (Claude Code's `.mcp.json`) lands there. Diagnostics runs `dettivo doctor`, shows the report line by line with the exit code as the verdict, and copies it.
- **Three surfaces are held to their artboards region by region; General stands for the pattern.** The visual manifest cuts Models, Hotkeys and Agents into two regions each right of the section column (the selections and the table, the bindings and the snippet with its panel, the fact panels and the host table), compared with the same rectangles of the artboards on Black Gold at both scales and with approved renders on the other four themes; General is a whole-window render approved on every theme for the five sections that follow the pattern.

## Consequences

- The Linux register gains `config.keys` and the `config.changed` topic with fixtures; `crates/dettivod/tests/config_live.rs` proves the topic on both paths. The contract replay stays at 0 failed.
- `settings_roundtrip` drives every key of every section through its own control on both drivers under Xvfb: the value reads back through `config.get` with source `file`, `config.unset` restores the default, the planted comment survives every write, a locked key shows its variable, an invalid value shows the refusal, a hand edit refreshes the open route with the notice, the column's action hands the file to `xdg-open`, the Agents write lands in the profile's home and Diagnostics names the daemon. Two keys are left to the file with the reason recorded in the evidence: `ipc.auth_mode`, because `peer_token` would lock the drive out of its own daemon, and `speech.provider`, which the model choice writes together with the model.
- The artboards show two things the schema does not have: a fifth binding row (`Open Dettivo`) on Hotkeys, and portal and evdev as two toggles where the schema has one `hotkeys.backend` choice. The route keeps a binding row's worth of air where the artboard has the row, and edits the backend as one choice; the visual regions are cut so both are compared on structure the schema supports.
- Live-desktop drives share the desktop's focus: a keystroke can land in another window when the focus moves between two keys. The drive raises and confirms the window before every edit; CI runs it under Xvfb with openbox, where the focus stays.
- Diagnostics shows what `dettivo doctor` prints and nothing more; a second diagnosis in the app would drift from the command line. The report's paths are the daemon's, shown relative to home.
