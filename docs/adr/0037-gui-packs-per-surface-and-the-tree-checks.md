# 0037. The GUI is proven by one pack of four surfaces, and every captured tree is scanned for developer text and unnamed controls

Status: Accepted 2026-09-05

## What this gives you

One command, `dettivo-qa pack gui`, walks onboarding, settings, history and the Omarchy plugin on both drivers in fresh profiles and writes one report that says, per surface, which steps passed, which screen leaked developer text and whether every control a user can act on carries a name. The same command is the phase 3 exit check on the development machine, the last step of the CI drive job against release-profile binaries, and the second named step of the release gate.

## Situation

Phase 3 ends with first run, settings, history and the plugin each proven by its own scenario, and the masterplan asks for them together: a GUI drive pack green under Xvfb and on the Hyprland desktop, every route's accessible text scanned for developer text in release builds (QA-4), and every interactive control named (NFR-9). The scenarios already capture a `tree-<route>.json` per screen and the `app_routes` drive already runs a five-class text scan on its own trees, but the classes were short of the list (no `debug`, no `parity_gap`, no stack frames, no raw JSON), the scan ran only where a scenario chose to call it, and nothing walked the trees for unnamed controls. The dictation pack of ADR 0017 runs one flat list of steps into one report; a GUI report needs to say which surface failed and what leaked where, and a settings failure needs to name the section, not the whole scenario.

## Decision

The GUI packs live in `crates/dettivo-qa/src/pack/gui.rs` on the pack model of ADR 0017. Every step carries a surface, and five packs exist: `gui-onboarding`, `gui-settings`, `gui-history`, `gui-omarchy`, each runnable alone, and `gui`, which runs the four in that order. A scenario step on the fallback driver must pass; the same step on cua-driver may skip with the reason, so a driver regression never hides a GUI failure. The settings round trip runs once per section as eight steps (`settings_roundtrip.<section>`, one scenario instance per section with the section's own checks), so a failing section is named with its key. Repository commands are steps too: the settings key lint, the plugin lint, and the shim load and version-skew tests through the design system's runner. `--surface <name>` narrows any GUI pack; an unknown surface exits 2 naming the four.

After every scenario step the pack scans each `tree-<route>.json` the step captured (`pack/scan.rs`): the negative text scan with the full class list (`negative_text::classify`: exception text, a stack-trace frame, raw JSON, a raw path, a model file name, an internal identifier including `parity_gap`, the word `debug`, a hash or an address), and the accessibility walk (`a11y_tree::check`): an element whose role a user acts on (button, toggle, check box, radio, text, combo box, slider, spin button, tab, list item, menu item, link) and which is on screen must carry a non-empty accessible name; static text and images are exempt. The walk's result lands beside the tree as `a11y-<route>.json`, and a finding of either kind fails the step naming the route, the class and the element. The scan carries one exemption, the drive's own profile root under `/tmp/dq`, because that path is the rig's location shown back where a user's machine shows a home-relative one; developer text that arrives from the daemon fails the route and is fixed in the product. `scripts/lint-release-text.sh` mirrors the same eight classes over QML literals.

The report adds `surfaces`: one block per surface with its steps, the routes scanned, every finding located by step, driver and route, and `a11y_coverage` as named over interactive with the offenders listed; `<pack>-pack.md` renders the block as a table. The binaries the pack drove are recorded with their build profile, and `scenarios::binary` prefers the newer of the debug and release builds, so `just build-release` before the pack makes it drive release binaries and the profile's `DETTIVO_QA_ALLOW_RELEASE=1` lets them accept QA mode. The profile preflight (`profile::guard`) refuses a scenario root that resolves under the caller's `HOME` or a real `XDG_*` directory by the variable's name, so a first-run drive never sees the developer's snippet, models or state.

## Consequences

- `just qa-pack gui` is the phase 3 exit check and the second step of the release gate (`docs/RELEASING.md`); CI runs it at the end of the drive job after `just build-release`, and the weekly job runs it on the fallback driver.
- Under Xvfb the Omarchy desktop steps (`omarchy_bar`, `omarchy_setup_idempotent`) and every cua step without the tool are allowed skips the report names; the plugin lint, the shim load and the version-skew tests pass everywhere.
- A GUI regression costs a named route and a named class or element in the report, on the surface it belongs to; a settings regression costs a named section.
- The scan has no allowlist beyond the profile root. A value the product must show verbatim and that trips a class (a model file name in a download row) fails the route and is a product decision, not a scan exception.
- The pack drives each first-run and settings scenario twice, once per driver, and the settings section steps start one app each: the GUI pack takes about ten minutes under Xvfb on top of the dictation pack.
- The Xvfb session (`scripts/qa/xvfb-session.sh`) is an X11 desktop whatever started it: it drops the caller's Wayland display and Hyprland signature and runs a session bus that activates no service, so the daemon probes the drive's own window and a token lookup through `secret-tool` returns at once instead of waiting out a service activation.
