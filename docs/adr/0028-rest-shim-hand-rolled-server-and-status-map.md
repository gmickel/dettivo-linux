# 0028. The REST shim is a hand-rolled HTTP/1.1 server over the router, loopback only, token on every request, with the macOS status map

Status: Accepted 2026-09-04

Amended by [0050](0050-private-transfers-authenticated-adapters-and-isolated-qa-processes.md), which forwards the resolved token to IPC, handles malformed authorization prefixes safely and makes REST status a readiness check.

## What this gives you

`curl -H "Authorization: Bearer $DETTIVO_IPC_TOKEN" http://127.0.0.1:45831/v1/system/health` works on Linux exactly as on macOS, and so does every other route, header and status code in `docs/api/dettivo-rest-v1.md`: a script, an editor extension or a browser tool written against one port drives the other. The shim is a few hundred lines that never go stale behind a framework, the daemon can host it from a service unit, and the fixtures prove every route against a live seeded daemon on every CI run.

## Situation

The macOS port ships the shim inside the app (`Dettivo/Services/REST/`): a loopback socket server on port 45831, `Authorization: Bearer` or `X-Dettivo-Token` compared with the token resolved in the hardened-mode order, `/v1/{namespace}/{method}` mapped onto the IPC adapter with query values coerced (`true`/`false`, integers, comma lists) and a JSON body overlaid, two streaming routes built on the transfer pipeline, and a fixed `app_code` to status map (400, 401, 404, 409, 429, 501, 503, else 500) with the JSON-RPC error object as the body. The masterplan (FR-S7) asks Linux for the same, off by default. The daemon's router (ADR 0002) and the MCP server (ADR 0019) already show that a hand-rolled protocol layer over `serde_json` is small and easy to hold to a contract; an HTTP framework would bring its own router, extractor and error vocabulary between the contract and the wire. The parser `httparse` is already in the dependency tree through `reqwest`. The macOS VS Code extension (`extensions/vscode-dettivo`) turns out not to call the shim at all: it writes the editor context to a file and runs voice-navigation commands; the request shapes an IDE bridge sends are the ones the macOS REST tests exercise.

## Decision

`crates/dettivo-rest` is a library that implements HTTP/1.1 by hand over `tokio` and `httparse`: a request head of at most 16 KiB, a body of exactly `Content-Length` bytes up to `[rest] max_body_bytes` (a longer declaration is answered `413` before the body is read and the connection closes), keep-alive with pipelined bytes carried to the next request, a per-request timeout, and one response with `Content-Length`. No HTTP framework crate, no TLS, no non-loopback bind: `[rest] bind` outside `127.0.0.0/8`, `::1` and `localhost` fails `config.validate` naming `rest.bind`, and the listener refuses a peer that is not loopback and a `Host` header that is not.

Every route calls one `Backend`: the daemon's own router when the daemon hosts the shim (`crates/dettivod/src/rest.rs`, `[rest] enabled = true`, started beside the socket and stopped at shutdown), or a one-connection-per-request Unix socket client when `dettivo rest serve` hosts it as a process. The route layer is the macOS one: `/v1/{namespace}/{method}` to `namespace.method` for `GET` and `POST`, the query coerced the macOS way and the JSON body overlaid, the catalog consulted so an unknown method is `404` and a reserved one reaches the daemon's `NOT_IMPLEMENTED` (`501`); `POST /v1/transcripts/import/stream` through `transfer.begin`, `transfer.chunk`, `transfer.commit` and `transcripts.import` with the macOS cancel reasons; `GET /v1/transcripts/export/stream` through `transfer.begin`, `transcripts.export`, `transfer.pull` and `transfer.commit` with the export's content type and an attachment filename. Events are not served over REST; `/v1/events/subscribe` answers `501` naming the socket and MCP.

The token is required on every request, always: the shim binds loopback but other users on the machine exist. It is resolved in the macOS order with the Keychain replaced by the Secret Service (`DETTIVO_IPC_TOKEN`, `secret-tool` item `service dettivo key ipc-token`, a `0600` token file), through `dettivo_core::token`, which the daemon's `peer_token` mode now shares; no token means no listener, with the three sources named. The status map is the contract's, applied to the error object the daemon produced; the one status the daemon never produces, `413`, carries `INVALID_PARAMS` naming the cap, and `APP_NOT_RUNNING` (`-32017`, `503`) is what the process-hosted shim answers when the daemon is unreachable, with the systemd hint.

`system.capabilities.rest` (`enabled`, `port`, `bind`) reports the daemon's listener, with `port = 0` taking an ephemeral port so tests never bind 45831. `dettivo rest serve | status | token` are the CLI verbs; `dettivo doctor` prints the row. The fixtures under `crates/dettivo-rest/fixtures/` are the proof: one file per request and answer, replayed by the crate's harness against a live daemon from the crate's test, from `dettivo-qa rest` and from the contract replay's REST section. The `vscode/` set carries the request shapes the macOS REST tests exercise for an IDE bridge (health, the latest transcript, one transcript, an insertion, the dictation state, an export stream).

## Consequences

- `dettivo-rest` depends on `dettivo-proto` and `dettivo-core` (the token and the `[rest]` schema); `dettivod`, `dettivo-cli` and `dettivo-qa` gain the edge to it (`tools/xtask/src/edges.rs`). `httparse` joins the workspace dependencies explicitly; `url` supplies the query parser.
- The `[rest]` section (`enabled`, `port`, `bind`, `max_body_bytes`, `request_timeout_ms`) is read at daemon start; changing `enabled` or `port` takes effect at the next start, which the documentation says. The QA runner's daemon always hosts the shim on an ephemeral port with a known token so the REST fixtures replay beside the socket ones.
- Query coercion is the macOS rule and stops there: a single value is a string, so a parameter the contract types as a list (`kinds`) is written as a comma list or in the body. The daemon validates every parameter exactly as on the socket, so the shim adds no second vocabulary.
- Defaults the macOS shim leaves to the adapter are fixed here for the import stream: `target_kind = dictation`, `mode = raw`, `language = auto`, and the filename from the query, the `X-Dettivo-Filename` header, then the content type. Both are registered in `docs/api/linux-deltas.md`.
- Concurrency is one task per connection and one blocking backend call per request, off the runtime's workers; a slow call holds its connection for at most `request_timeout_ms` and the answer is `500` naming the key.
- The VS Code extension smoke on a desktop is a documented manual step (`docs/rest.md`): the extension does not call the shim, so the fixtures under `vscode/` are the request shapes an IDE bridge sends, replayed on every run; a bridge that does call the shim is proven by the same set.
- Proof: `crates/dettivo-rest/tests/harness.rs` runs the fixtures against the daemon-hosted shim (the live import through `tiny.en` when the test model is present) and against a process-hosted shim over the socket, proves keep-alive with two pipelined requests, the `503` with the systemd hint once the daemon is gone, a second server on the port failing naming it, and a daemon with `[rest]` enabled but no token hosting nothing; `dettivo-qa rest` and the contract replay run the same fixtures in CI's `drive` job.
