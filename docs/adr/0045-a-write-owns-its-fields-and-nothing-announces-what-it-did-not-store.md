# 0045. A write owns the fields its operation changes, and nothing announces what it did not store

Status: Accepted 2026-09-06

## What this gives you

Notes you type while a meeting records survive every checkpoint, the stop and the speaker pass; a delete removes exactly what its policy names and says so only when it did; a finalisation that cannot store its transcript keeps the audio for a retry instead of announcing a completed meeting; and the same rule holds for the app's state file, an export over an existing file, the pill's completion, a refused model action and a fine-tune conversion. This record closes the seventeen data-loss findings of the cross-model review (`docs/reports/reviews/2026-09-06-astra/`, spec fn-43) and names what changed in earlier decisions.

## Situation

The review read main 28b4b7d and found the same shape of defect in fourteen places: a component held a copy of some state, wrote the whole copy back later, and erased what another writer had stored in between; or it cleaned up, announced success and only then tried to store, so a storage failure left the announcement standing and the inputs gone. The capture worker rewrote every meeting column at each checkpoint (ADR 0036 had given the notes and the analysis setters of their own, but `update_meeting` still wrote those columns from the worker's stale row); the finalisation removed the checkpoint and applied the audio policy before the final row was stored; the analysis dropped its job entry before writing its result, so a transcript-only delete could not cancel it and the old summary came back; a delete removed the row before the directory; a meeting row and its speaker table changed in separate statements; unreadable JSON read as empty data; the CLI turned a failed configuration lookup into the `all` delete policy; a dictation take's result lived in one slot every start reset; the app wrote its load-time copy of the daemon's state tables back on close; the export truncated the destination before the first chunk; an old take's completion applied to the next take; a refused model action was cleared by the refresh that followed it; the conversion script removed the previous model before converting; and the QA rig levelled every value to one marker and lost the model checksum it reported. Every claim was verified against the code and a test before it was fixed; none was rejected.

## Decision

A write owns exactly the fields its operation changes. In the store, `update_meeting` rewrites the twenty-eight columns the capture, the transcription and the speaker pass own and leaves the summary, the notes and the analysis to their setters; the row and its speakers change in one transaction, and the speakers are replaced only when they differ. A JSON column that does not parse is an error naming the meeting and the column, never empty data, so a read-modify-write cannot rewrite a payload it could not read.

Nothing announces success it did not store. A finalisation stores its settled row first and only then removes the checkpoint and applies the audio policy; a store that refuses the row keeps the takes, ends the meeting failed with the storage error and starts nothing that follows a completion. The analysis and the speaker pass commit through one job registry per meeting (`crates/dettivod/src/meeting_jobs.rs`): a result is written only by the job that still owns the meeting, under the lock a cancel or a delete takes, so a delete invalidates every job for the meeting and a late job neither restores what was cleared nor removes a newer job's entry. A dictation take completes through a completion object of its own, created before its source opens, and every stop or cancel waits on it.

A delete removes exactly what its policy names. The directory goes before the row, so a directory that cannot be removed keeps the row addressable for a retry; the audio-only policies treat only a missing directory as nothing to remove and propagate every other error, so the audio facts stay true while the takes stay. The policy itself is resolved by the daemon: `meetings.delete` without `artifact_policy` takes `[meetings] delete_artifact_policy` (an additive Linux delta registered in `docs/api/linux-deltas.md`), and `dettivo meetings delete` sends no policy unless one is given.

The same rule on the hosts and the scripts: the app's state save reads the daemon's tables fresh from the file at that moment and never writes a load-time snapshot back; an export writes one `QSaveFile` and commits it at the last chunk; a completion waiting out the pill's Transcribing beat applies only to the take it belongs to; a refused model action keeps its reason until the next attempt answers; and `convert-polish-finetune.sh` builds, checksums and verifies in a staging directory and publishes only a complete model.

The QA rig tells the truth about what it compared: every scenario daemon starts from the profile's baseline (`[hotkeys] backend = "none"` unless the scenario names a backend), a shape-compared replay keeps every leaf's type and every list's row structure, and the polish eval hashes the candidate while its profile still exists, failing the report for a real candidate it cannot hash.

## Consequences

ADR 0036 is amended: the delete policy for a request that names none is the daemon's, not each client's, and the whole-row update no longer touches the notes, the analysis or the summary. ADR 0035 is amended: `meetings.delete` invalidates a running speaker pass, and a `meetings.cancel` still lets it record its cancelled block. ADR 0027 and ADR 0030 are amended: a finalisation's storage failure is a failed meeting with its audio kept, and a delete's order is directory then row. ADR 0024 is amended: the app no longer preserves the daemon's state tables from load; it reads them at save. ADR 0032 is amended by the staging directory. ADR 0043 is amended: the profile's baseline configuration reaches every daemon `DaemonHandle` spawns.

A meeting row whose stored JSON does not parse is now a visible error on `meetings.get`, `meetings.list` and every read that attaches it; before, it read as an empty transcript and could be rewritten as one. A finalisation whose store is unavailable ends failed instead of completed and keeps its takes; the retry is `meetings.recover` on a partial meeting or a new finalisation, and a failed meeting's own retry path stays the subject of review finding meetings/F5. A contract replay that compares by shape now fails on a wrong scalar type or a malformed row where it passed before; a fixture that legitimately varies keeps passing through the empty-list and null tolerances. The analysis and the speaker pass hold the meeting's job lock for the duration of their final store write, which is one row update.
