# 0051. The release gate passes on validated evidence bound to the tested binaries, and an unexplained failure stays a failure

Status: Accepted 2026-09-06. Amends 0030 (the plugin mirror), 0034 and 0040 (what publishes), 0039 (how `--record` files the meetings block) and 0041 (the gate's classification rules and the evidence map's claim); the receipt requirement is superseded by [0070](0070-a-release-is-local-qa-and-a-tag.md)

## What this gives you

A green release gate now means what the runbook says it means: every receipt it reads is typed and complete, every binary it drives is the release build of the gated commit, every failed row stays a failure whichever driver ran it, and a tag publishes only when the gate's own receipt is checked in for the code being shipped. A person reading `docs/reports/release-gate/<version>.md` can trust that a pass was earned rather than inferred, and a person rehearsing a release cannot publish by accident.

## Situation

The cross-model review of main `28b4b7d` (ten gpt-6-astra area reviews, kept under `docs/reports/reviews/2026-09-06-astra/`) put sixteen findings on the release gate and its evidence, and the checked-in 0.1.0 run confirmed them: `install_test` judged a receipt by "no row says fail", so `{"passed":true,"steps":[]}` passed and a missing report became an external blocker through the word `--session`; `bench_report` passed on two filenames, the 2026-09-06 GPU report was a copy of the 2026-09-05 one under a new date, and `in_history` was computed and ignored; `pack_meetings` was recorded as passed after exit 1 because a row that failed on `cua-driver` while its `atspi` twin passed was excused by name; `ci_green` read a 404 as "the workflows are disabled" without asking; the drives took whichever of `target/debug` and `target/release` was newer while the report carried the checkout's `HEAD`; the startup benchmark timed the profile preparation; the accessibility walk dropped every control whose extents failed to read and a surface with no captured tree reported coverage 1.0; the evidence map resolved a `unit` reference to any function of that name and a `human` reference to any existing file; the style check returned the first delegate that had a document; the Parakeet build patched a caller's `PARAKEET_CPP_SOURCE_DIR` in place; a dispatch against the tag with `dry_run=true` published; nothing in the workflow read the gate's receipt; and the docs promised a plugin mirror the release never wrote. The daemon's own contract test copied the fixture's search rows over the daemon's.

The alternative on the table for several of these was a note in the report. The decision here is that a gate is not a place for notes.

## Decision

- **Receipts are typed and complete.** `gate::judge` deserialises the install test's report and requires the seventeen named checks present once and passed with exit 0, the version and package of this release and `passed` true; a skipped check, an unknown status, a nonzero exit on a pass, a duplicate row, another version's receipt or a missing file fails the step naming the fact. `release_bench::judge` reads each tier's newest report per host as the typed benchmark report and requires a parse, the right tier, steps with none failed or valueless, a commit and a meetings block both in this history, and the meeting and diarization factors; the CPU tier accepts a clean report from any host, so a CPU-only machine's evidence lifts the desktop's forced row, and no other file stands in for a newest one that fails.
- **Evidence is filed in place, never copied forward.** `pack meetings --record` writes its block into the latest benchmark report for the host and tier; the file keeps the benchmark's date and commit and the block carries the pack's. The 2026-09-06 GPU copy is folded back into the 2026-09-05 report it duplicated. The `diarization` placeholder step is gone from `dettivo-qa bench`; the meetings pack's `diarization_throughput` is the measurement.
- **A failed row is a failure.** `judge_pack` fails a pack step on any failed row whichever driver ran it; the "failed on cua-driver" classification rule is deleted. An `atspi` pass does not establish that a `cua` failure belongs to the driver, so the gate keeps the failure and a person diagnoses it. The three meetings screens that fail on `cua-driver` in the 0.1.0 record are therefore open defects, not exceptions.
- **Unavailable GPU attribution names the missing evidence.** The meeting pack's GPU proof step skips when its counter sees only a process allocation or aggregate utilization. The release gate classifies those two explicit reasons as external, requiring a per-process workload counter that attributes inference execution to the tested engine. The classification applies only to `pack_meetings/gpu_workload_proof`; another step or an unknown attribution error stays unexplained. The proof remains skipped and its raw samples stay in the report. A failed GPU row still fails the gate, even when its reason also describes an external counter limitation.
- **Missing CI evidence is not a disabled workflow.** `ci_green` asks the repository permissions API when it finds no run or `gh` fails, then queries the primary `.github/workflows/ci.yml` workflow if repository-wide disablement was not confirmed. The blocker is external only when one of those API responses positively confirms disablement; the report retains the workflow path, ID and state. Active, unrelated or unknown workflow responses leave missing evidence unexplained. A known failed run stays a failure even after disablement. This covers the deliberately disabled CI workflow while Copilot remains active; it does not turn missing CI into a passing run. A `gh` that is not installed stays a missing tool.
- **The binaries are chosen once and named.** A drive launches `target/<profile>/` for `DETTIVO_BUILD_PROFILE` (`debug` unless it says `release`), never the newer file; `pack release` pins `release` for itself and every verb it spawns, records each binary's SHA-256 and the commit `dettivo --version` embeds, and refuses to start when `dettivod` or `dettivo` is not the release build or the CLI's commit is not this checkout's. The rig sets the variable for the GUI pack after `just build-release`.
- **The startup figure is the daemon's.** `BenchDaemon::prepare` builds the profile, links the models and writes the environment outside the clock; `Prepared::spawn`, from the process spawn to the answered ping, is what `startup` times.
- **Coverage counts what was seen.** An interactive control whose geometry the driver could not read stays in the walk and has to carry a name; only a control at zero size is hidden. The AT-SPI snapshot fails rather than returning a smaller tree when it hits its depth or size limit or cannot read a child. The scanner reads `tree.json` as the `window` route, an empty tree is a finding beside an unreadable one, a GUI step that passed without capturing a tree fails as not inspected, and a surface with no inspected tree reports `a11y_coverage` as null.
- **The map is an inventory.** A `unit` reference must carry `#[test]` or `#[tokio::test]`, a `visual` reference may name a state as `surface/state` and is checked against the manifest, a `human` reference resolves as the receipt it is, and the report says so: routes that exist, not routes that passed. The duplicate name lists are gone; `bench` and `pipeline` routes resolve against the registries the verbs use.
- **Each delegate is judged on its own.** `styleFindings` checks a control's background and content item independently and names the delegate; the `basic_background` and `basic_content` plants prove both on the sheet, the pill and the bar.
- **A supplied source tree is read, never written.** `crates/parakeet-cpp-sys/patch.rs` patches the tree the build fetched once and only checks a tree named by `PARAKEET_CPP_SOURCE_DIR`, stopping the build with the command to run when the ggml CPU patch is missing; the rule is tested without a compiler in the loop.
- **Publication follows the receipt.** `scripts/packaging/release-decide.sh` publishes on a tag push or a dispatch with `dry_run=false` on that tag and rehearses otherwise, whatever ref it runs on; `scripts/packaging/release-receipt.sh` requires `docs/reports/release-gate/<version>.json` to say the gate passed for this version with no failed step and no unexplained blocker at a commit the released one descends from with nothing but `docs/reports/` changed since. It reads the report and the history only, so it never waits for its own run. `scripts/packaging/test-release-scripts.sh` proves both in the packaging lint.
- **The mirror is a hand step, named as one.** No workflow writes `gmickel/omarchy-dettivo`; `scripts/omarchy/export-plugin.sh` is the releaser's last step after the tag and the runbook says so. A publication stage returns when a rehearsal into a disposable checkout has compared the exported tree byte for byte.
- **The daemon's contract test asserts the seeded search.** The rows deserialise as the protocol types, the fixture's hit has to be among them and its snippet inside the answer's, and nothing is copied from the fixture into the answer; an empty result and a mistyped row fail by name.

## Consequences

- The 0.1.0 record is no longer a passing run under these rules: its meetings step has three failed `cua-driver` rows, its benchmark reports were measured on squashed branches, and its `ci_green` blocker was never confirmed. The next gate run on a commit of this history, after `just bench` and `just qa-pack-meetings --record` on it, is the run of record; the checked-in report stays as the history it is.
- `just bench` on a branch that is later squashed produces a report the gate rejects; the benchmark rows are measured on a commit of `main`, which is where the release is cut.
- Receipts from an install test that skipped `zsh` or `fish` completions, or any other required check, fail the gate; the machine running the test installs what the check needs.
- A CPU-only machine's benchmark report clears the desktop's forced CPU row by landing under its own host name; the `install_test` blocker for the `--session` run still needs that machine's receipt through `DETTIVO_INSTALL_TEST_REPORT`.
- `DETTIVO_BUILD_PROFILE` is one more variable to set when a debug tree and a release tree both exist; the recipes and the rig name it where it matters.
- The release workflow's `prepare` job checks out full history (`fetch-depth: 0`) for the receipt walk; a tag pushed without the gate's report for its version fails in `prepare` before a crate compiles.
- A supplied Parakeet checkout has to be patched by its owner once; the build names the command.
