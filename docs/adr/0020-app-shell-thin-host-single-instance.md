# 0020. The app is a thin host around the shared module, one window per session, proven by name

Status: Accepted 2026-09-04; Home's visual check moved into the matrix by [0052](0052-qa-isolation-and-honest-assertions-every-check-proves-what-it-claims.md)

## What this gives you

The desktop app opens in a few hundred milliseconds looking like the rest of your Omarchy desktop, keeps one window per session that any launcher click or `dettivo app open` lands in, survives the daemon restarting under it, and every route of it can be opened by name and checked by a drive from the first commit.

## Situation

The masterplan fixes the app as a Qt 6 Quick application with a thin C++ host (FR-U1): window, JSON-RPC client with the event subscription, list models, settings binding, with every visible thing in the shared `Dettivo` QML module (ADR 0010) so the Omarchy bar plugin can use the same pieces. Twelve routes exist (FR-U2) and only Home has an approved baseline (`home.png`); the rest are filled by later specs. The pill (ADR 0015) had already built a daemon client with reconnect and a control socket under `qt/host/osd/`, so the app would either copy or share them. The daemon's `transcripts.list` items carry the contract's fields only (no app, no mode), and the seed's rows are dated in February, so a render of Home against a live daemon can never match the baseline's rows. The QA rig looks elements up by accessible name on two drivers (ADR 0011), and its release-text lint reads QML literals, not values that arrive from the daemon. The startup and theme budgets (300 ms, 60 MB, 100 ms) are a desktop's numbers; CI runs on slow containers.

## Decision

- The daemon connection (`DaemonClient`, `DaemonLink`) and the path resolver move to `qt/host/daemon/`, one static library the pill and the app link; the termination-signal helper joins the shared host library. `OsdSettings` keeps its path functions as forwards so nothing in the pill changes shape.
- The app host lives under `qt/host/app/`: `Router` (the route names, their titles, a history stack), `StatusModel`, `EnginesModel`, `HistoryModel` with `NewestDayModel`, `ConfigBinding`, `AppState` (`state.toml`), `AppControl` (the instance socket) and `AppJournal`. `AppHost` is the QML singleton compiled into the `dettivo-app` module that hands them to `Main.qml`; the shared screens under `qt/qml/Dettivo/app/` take them as plain object properties, so the Quick Tests hand in fakes and the bar plugin can reuse a screen with its own objects.
- Routes are one table in `Router`: `onboarding`, `home`, `history`, `history.detail`, `meetings`, `meetings.live`, `meetings.detail`, `settings` with eight sections, and `agents` as the sidebar's alias for `settings.agents`. `--open`, `DETTIVO_E2E_OPEN`, the instance socket and the sidebar all go through `Router::parse`; an unknown name exits 2 from the app naming the routes, and `dettivo app open` refuses it locally with exit 4, the command line's code for bad arguments. The QA parsers on both sides (`dettivo_core::qa`, `qt/host/qa_environment.cpp`) accept the detail and meeting routes and any `settings.<section>`; the app is the one that knows the sections.
- One window per session: `app.sock` beside the daemon socket answers `raise`, `open` and `status` in one JSON line. A second `dettivo-app` forwards its request and exits 0 before creating a `QGuiApplication`; `dettivo app` does the same and launches the binary (beside `dettivo`, then on `PATH`) in its own process group when nothing answers. A socket file nobody answers on is a crash's leftover and is replaced.
- The daemon-unavailable state is a banner over every page plus the Home sentence, shown after a grace of 1.5 s so a restart inside the client's first backoff shows nothing, cleared on the first answer; every model re-reads its facts on reconnect. The window never goes blank: the routes render with empty models.
- Home matches `home.png` through a sample: `dettivo-app --render <png> --sample --open home` fills the models with the baseline's facts (`sample_data.cpp`) and no daemon. The four regions (sidebar, header with the strip, Today, the rail) were first compared by a script of their own on two themes at 1x; since ADR 0052 they are the `home` surface of the visual matrix (ADR 0021, `qa/visual/manifest.toml`) on every theme and scale. The live daemon proves the data path in the drives; the sample proves the layout in the matrix.
- The negative text scan of the rig runs on the live accessibility tree (`dettivo_qa::negative_text`, the classes of `scripts/lint-release-text.sh`) on every route the `app_routes` drive opens, so a path or a model file name that arrives from the daemon is caught where the QML lint cannot see it. The engines rail therefore shows model ids reduced to their names, never paths.
- The app journals its own measurements under QA mode (`$XDG_STATE_HOME/dettivo/qa/app.jsonl`): the first frame from the process's entry to the first `frameSwapped`, the theme apply time from `ThemeBackend::themeChanged` to the next swapped frame, the resident set after five seconds. The drives record them in `startup.json` and `theme.json` on every run and assert the budgets only under `DETTIVO_TIMING_GATE=1`, which `just qa-app-timing` sets on a desktop; CI records without asserting because its runners are not the machine the budgets describe.
- Window chrome is left to the compositor: no `FramelessWindowHint`, no decoration override; Qt's xdg-decoration negotiation yields server-side decoration on Hyprland and the other wlroots compositors, and the scale factor rounding policy is pass-through so fractional scales render at their real value.

## Consequences

- The pill's host shrank by the daemon client and the signal helper and gained nothing; the app added one static library and twelve screens under 300 lines each, all on the module's tokens (the frame's sizes are tokens now: `sidebarWidth`, `pagePaddingX`, `rightRailWidth`, `instrumentStripHeight`, `appWindowWidth`, `appWindowHeight`).
- On the development machine (Hyprland, NVIDIA) Home's first frame lands in 210 to 290 ms on Wayland and under Xvfb's X11 alike: the application object takes about 35 ms, the QML module about 120 ms, the first swapped frame the rest. The resident set after five seconds is 240 to 310 MB there, of which the process's own pages (anonymous, `Pss_Anon`) are about 31 MB and the rest is the NVIDIA driver's code mapped by every GL client (`libnvidia-gpucomp`, `libnvidia-glcore`: 70 to 100 MB resident, shared and clean) plus the Qt libraries; the software scene graph brings it to about 210 MB, so the driver is loaded either way. The budget of FR-U7 names the resident set, so `startup.json` reports it beside the proportional and anonymous sets, and `just qa-app-timing` fails on this machine on that number alone; the first frame and the theme apply pass. The number to watch for a regression is the anonymous set.
- The sample render fixes the layout, not the data: a daemon whose `transcripts.list` carries different rows renders different text in the same structure, which the comparison is blind to by design. A change in Home's structure fails the CTest case and CI's `unit-qml` job until the baseline is re-approved and re-cut.
- `dettivo app` and the second-launch path depend on `app.sock` living beside the daemon socket, so a QA profile isolates the app through `DETTIVO_IPC_SOCKET` alone, like the pill.
- The three timing budgets are asserted on a desktop only; a regression that only shows on a slow machine is visible in CI's evidence, not in its verdict.
- The bar plugin (S-21) reuses the daemon library and the screens through their object properties; it owns its own host objects, so nothing here assumes a single process.
