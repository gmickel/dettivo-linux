# 0024. First run is three screens of config writes, shown only when a key or a model is missing, with one allowance to dictate into itself

Status: Accepted 2026-09-04, amended 2026-09-06 by 0049 (first run downloads the local model through llm.models.download)

## What this gives you

A fresh machine dictates within three screens: Keys shows the exact binding snippet the daemon will write and confirms live when you press the key, Models downloads one verified speech model and optionally picks the Enhanced model, Try it lands your first sentence in a field inside the app and names the backend and the time it took. A machine provisioned with a `config.toml`, a snippet and a model directory never sees any of it, and everything the screens do is a config write or a download you could have made by hand.

## Situation

The masterplan fixes first run as three screens and nothing more (FR-U3) and every step as a config write plus a model download (FR-C5), so dotfile provisioning stays first-class. The pieces the screens need already exist behind the socket: `dettivo setup <compositor>` renders and writes the compositor snippet from `[hotkeys]` (ADR 0016), `speech.models.*` downloads and verifies a catalogue model and `speech.selection.set` writes `[speech]` (ADR 0004), the Enhanced pass reads `[llm] provider` (ADR 0023), and the app's `onboarding` route was a scaffold waiting for its screens (ADR 0020). Three things stood in the way. The snippet generator lived in the CLI, so the app could only have shelled out to it or drifted from it. The insertion chain refuses Dettivo's own windows (`target_is_self`, ADR 0007), which is right everywhere except the one field first run wants to dictate into. And the app and the daemon both wrote `$XDG_STATE_HOME/dettivo/state.toml` with a schema that refused the other's tables, so a completion mark written by the app was erased on the next daemon start. The three screens were designed and approved (`first-run-1-keys.png`, `first-run-2-models.png`, `first-run-3-try-it.png`), and the design shows paths (`~/.config/hypr/dettivo.conf`) that the release-text scan classed as developer text.

## Decision

- **The trigger is a decision the app makes from three daemon answers on every start** until a completion is recorded: `speech.models.status` (a speech model, never a VAD model, is `ready` or `unverified`), `hotkeys.status` (the daemon backend bound actions) and `hotkeys.setup { write: false }` (the compositor snippet is sourced). First run is required when no model is ready or when neither a backend nor a snippet delivers the keys. A machine that passes the check gets `first_run.completed_at` written at once so the check never runs again; a machine that fails it opens `onboarding` instead of Home, and a flow closed mid-way records its `step` and reopens there. `DETTIVO_E2E_COMPLETE=1` marks it complete, `DETTIVO_E2E_STEP=keys|models|try` opens a step by name, and `dettivo app open onboarding` reopens the flow on a provisioned machine.
- **The snippet has one generator, in `dettivo-hotkeys`.** `hotkeys.snippet` renders it and `hotkeys.setup` writes it (a file that already holds the same text is left alone; the main configuration is never edited) and reports what `dettivo setup --check` reports; the CLI calls the same `snippet::write` and `snippet::check`. Keys shows the daemon's text verbatim, so the drive's golden is `dettivo setup hyprland --stdout` byte for byte. Off Hyprland, Sway and Niri the daemon answers `INVALID_PARAMS` naming the supported compositors and the step shows the portal's outcome from `hotkeys.status` instead of a snippet.
- **A press is confirmed from what the daemon already reports.** On the compositor path the `dictation.state` transition into `recording` is the confirmation; on the portal and evdev paths `hotkeys.status.last_press_at`, set by the daemon's own action path, is polled once a second while Keys is on screen.
- **Models offers the catalogue's shortlist.** A model with a `recommended_for` line in the catalogue (`parakeet-v3`, `large-v3-turbo`, `small.en`) is offered, plus any model already ready or selected; the GPU tier from `system.capabilities.platform.gpu` names the default (`parakeet-v3` on Vulkan, `small.en` on the CPU). A pick writes `[speech]` through `speech.selection.set` and starts `speech.models.download`; the `model.download` events, now published on the stream four times a second, drive the progress hairline; the step completes when the selected model is ready. The Enhanced tick writes `[llm] provider` (`local`, `ollama`, or `auto` when unticked); the local model's download is a hook that fires when the daemon declares `llm.models.download`, and until the local engine spec lands the local row carries the provider's own detail and the Ollama row the probe's.
- **Try it dictates into the app through one explicit, bounded allowance.** `insert.allow_self_target { enabled }` arms it on the calling connection, and only a peer whose process is `dettivo-app` may arm it (any peer under QA mode); while armed, a dictation whose key went down over the app's window ids (`dettivo`, `dettivo-app`, never the pill's or the sheet's) and an `insert.perform` that sets `allow_self_target` land in it. The app arms it when the step appears and disarms it when the step leaves or Done is pressed; the daemon disarms it when the connection closes. Everything else about the chain is unchanged: the guards, the backends, `target_is_self` for every other window.
- **The state file is shared without either side erasing the other.** The daemon's `State` keeps every table it does not own through a save, and the app's `AppState` carries the daemon's tables through its own; `[first_run]` holds `completed_at` (ISO 8601 UTC) and `step`.
- **The three screens are held to their artboards region by region.** The visual manifest's `first-run` surface renders each step with the baselines' facts (`DETTIVO_E2E_SEED=1` under `--render` applies the sample, the way `--sample` does for Home) and compares three regions of every screen (header, body, footer) with rectangles cut from the step's own artboard; a manifest state may name its artboard and its rectangle, and the runner cuts the render to it before the diff. Catppuccin Latte and the two built-in palettes are approved renders.
- **A path the user is told about is user text.** The release-text lint and the negative text scan keep flagging absolute paths (`/home/`, `/tmp/`, `/usr/`, `/var/`) and bare hidden directories, and accept a home-relative path (`~/.config/dettivo/config.toml`) and a quoted path inside a configuration line; the app shows every path it gets from the daemon relative to home or to the XDG variable it sits under.

## Consequences

- Two Linux additions join the register with fixtures: `hotkeys.snippet` and `hotkeys.setup`, `hotkeys.status.last_press_at`, and `insert.allow_self_target` with `insert.perform.allow_self_target`; `speech.models.status` rows carry `kind`, `languages` and `recommended_for`. The contract replay stays at 0 failed.
- The allowance is the one hole in `target_is_self` and it is shaped to close itself: connection-scoped, app-only outside QA mode, limited to the app's window ids, disarmed on the step's exit and on disconnect. `crates/dettivod/tests/insert.rs` proves the refusal outside the step and the `notTheApp` conflict for any other peer.
- Provisioning stays a `config.toml`, a snippet and a model directory; the completion mark is runtime state in `state.toml`, so a dotfile manager that ships neither sees first run once and never again.
- The drives prove the whole path on both drivers: `first_run_fresh` (Keys with the golden snippet and the live press, Continue writes the file once, the catalogue rows, a pick writes `[speech]` and downloads the test model from a loopback fixture server that serves the machine's tiny.en under another id, the mock microphone lands in the field through the real chain, Done records the completion and opens Home) and `first_run_provisioned` (Home, no first run, completion recorded). On a live desktop where the user keeps working, the focus can move during the take; the drive then hands the transcript over again through the guarded chain into the app's window and records `focus_moved_during_take`, which under Xvfb never happens.
- The drive's models directory lives under the repository's `target/` behind a link in the profile's data home, because `/tmp` on the development machine carries a user quota that a second copy of a model exhausts; the fixture server serves the real file in place.
- Hyprland 0.56 reads dispatches as Lua, so the rig's focus helper sends `hl.dsp.focus({ window = "pid:<pid>" })` first and the classic `focuswindow` form to an older Hyprland; the cua driver's click coordinates on a multi-output desktop are not this record's to fix, and the fresh drive's clicks are proven on the in-repo driver here and on both drivers under Xvfb.
- A model the engine cannot load (a corrupt download) leaves `dettivo-engine-whisper` answering `load_failed` for the next good model too until the daemon restarts it; the drive avoids the case by serving a loadable model, and the engine's recovery after a failed load is a follow-up for the engine spec.
