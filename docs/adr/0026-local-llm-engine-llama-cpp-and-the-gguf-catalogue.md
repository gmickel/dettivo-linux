# 0026. The local language model runs llama.cpp through the engine protocol, with the macOS catalogue in GGUF, and is the default provider once a model is on disk

Status: Accepted 2026-09-04, amended 2026-09-06 by 0048 (a stop string's prefix is never streamed)

## What this gives you

Enhanced dictation works with nothing installed beyond Dettivo: `dettivo llm download --model qwen3-4b-instruct-2507` fetches one verified file, and from then on every rewrite runs in the daemon's own `dettivo-engine-llm` process on the same Vulkan backend the speech engines use, with the same guards and the same fallback to the deterministic Polish text. The model is chosen from the catalogue macOS ships (Qwen3 4B Instruct 2507 by default, 1.7B for speed, 4B for quality, 8B for meeting analysis), the GPU memory it holds comes back ten minutes after the last rewrite, and `dettivo llm engine` and `dettivo doctor` say what is loaded where and why.

## Situation

ADR 0005 decided a local language model for v1 with the macOS models, and ADR 0023 shipped the provider layer with a `local` slot that reported itself unavailable. Omarchy machines rarely run Ollama; without this engine the default Enhanced experience was a fallback notice. The engine protocol (ADR 0003) already carried `generate` and `partial` shapes as placeholders, the supervisor already spawned, warmed, reaped and restarted engine processes, and the catalogue already downloaded and verified files into `<models>/<provider>/<id>/`.

Two things had to be decided. The binding: `llama-cpp-2` (utilityai/llama-cpp-rs) tracks upstream llama.cpp within days, publishes a release most weeks (0.1.156 on 2 September 2026, 1.2 million downloads), vendors the llama.cpp source in its `-sys` crate with the same `vulkan` feature parakeet.cpp's ggml exposes, and forwards `CMAKE_*` and `GGML_*` environment variables to CMake the way the Parakeet binding does; a hand-rolled binding would have been a second copy of that work. The shape of a streaming request: the speech engines answer one request at a time and a `cancel` waits for the next request, which is fine for a recognition that finishes in a second but not for a generation that a slow model can stretch past the eight-second budget the Enhanced pass has.

Two smaller questions came with them. Where the catalogue lists language models: a sibling file would have meant a second parser and a second download path. And where the `local` provider gets its engine: `dettivo-language` must not spawn processes, and the supervisor lives in `dettivo-speech`.

## Decision

`crates/dettivo-engine-llm` is the third ggml engine, on `llama-cpp-2` pinned at `=0.1.156`, built for the CPU by `just build` and with `--features vulkan` by `just build-llm-vulkan`, which CI runs as the advisory `llm-vulkan` job beside `whisper-vulkan` and `parakeet-vulkan`. `load` names the model file and, new to the protocol, a `context_length`; the engine puts every layer on the Vulkan device with the most memory (a discrete GPU before an integrated one) when the build carries the backend, a device enumerates in ggml and the file fits the device's free memory, and otherwise loads on the CPU with the reason in `loaded` (a Vulkan load that fails under `auto` retries on the CPU; `vulkan` fails the load instead). A missing model is `model_missing` naming the path; a corrupt one is `load_failed` naming the path and llama.cpp's reason.

`generate` replaces the placeholder shape: `prompt_profile` (`polish` runs `system` and `user` through the model's chat template with an empty thinking block prefilled for a Qwen3 thinking model; `raw` feeds `user` as is), `max_tokens`, `temperature` (greedy at 0; top-k 20, top-p 0.8 and a fixed seed otherwise) and `stop` strings, answered with `text`, `tokens`, `finish_reason` (`stop`, `length`, `cancelled`) and `backend`. The engine returns the raw text; the language crate's guard strips thinking blocks, as ADR 0023 has it. `status` gains `memory_bytes`, the bytes in use on the model's device as ggml reports them.

The language model binary keeps reading frames while it generates: `dettivo-engine-proto::host_llm` is the streaming counterpart of the speech host, with a reader thread feeding a channel that the token loop drains between two tokens. A `cancel` for the running request ends it there and the answer so far comes back `cancelled`; a `status` meanwhile answers `busy` with the memory figure; any other request waits its turn and is answered afterwards, in order. The daemon's `LlmEngine` (in `dettivo-speech::llm`, beside the supervisor it drives) sends that `cancel` when a `generate` outlives `[llm] timeout_ms`, so the process is free for the next request while the Polish text goes in with `provider_unavailable`. A context is created per `generate` and dropped after it, so only the weights stay on the device between requests.

The supervisor reaps the LLM slot on its own timeout, `[engines] llm_idle_seconds` (600 by default, beside `stt_idle_seconds`; the spec's `[engines.llm] idle_unload_seconds` is folded into this key, which was already shipped and documented), sends `unload`, logs an engine that does not answer it and ends the process regardless. `[engines.llm]` carries `backend`, `context_length` (4096) and `max_tokens` (1024).

The catalogue stays one file: `crates/dettivo-speech/catalogue/v1.toml` gains an `llm` provider with `kind = "llm"` and a `roles` list (`polish`, `analysis`), and the four models are the Q4_K_M GGUFs of the unsloth conversions of the Qwen releases (Qwen publishes no GGUF for 4B Instruct 2507 and only Q8_0 for 1.7B), verified by SHA-256 and Apache-2.0 licensed. `llm.models.status|download|cancel|delete` are the speech shapes over that provider with `is_selected` marking `[llm] model` and an unknown id answered `NOT_FOUND` naming the ids the catalogue lists; the speech methods filter to the providers with a speech model, so a language model never shows up as a dictation choice. `[llm] model` selects the Enhanced model and `[llm] analysis_model` the analysis one (empty means the same).

The `local` provider takes its engine through a trait: `dettivo-language::provider::LocalEngine` (`model`, `probe`, `generate`), implemented in the daemon by `LocalLlm`, which binds `[llm] model` to the supervisor and reports availability as the file on disk, the binary found and the engine not degraded. `pipeline::Settings` carries the engine, `polish.test` and every session pass the daemon's, and `auto` prefers `local` the moment it probes available. A process without the daemon (a test, a CLI) gets a detached provider that reports itself unavailable. `system.capabilities.llm.local_available` is that probe.

## Consequences

`llm.models.*`, `llm.engine.status`, the `local_available` flag and the eight `llm.methods` are registered in `docs/api/linux-deltas.md` with fixtures; the five machine-specific ones are covered by `crates/dettivod/tests/llm_models.rs` rather than replayed. `dettivo llm download|cancel|delete|status|engine|test` and a `dettivo doctor` row expose them.

The model-backed tests (the engine's protocol, partials, cancel and CLI mode; the daemon's `polish.test`, an Enhanced dictation and the goldens report) run on a machine that has fetched `llm/qwen3-1.7b` with `scripts/models/fetch-llm-test-model.sh` and skip by name without it; CI builds the CPU engine and runs the rest. `docs/reports/llm-goldens-report.json` records what the 1.7B model made of the eighteen Polish golden cases through `polish.test` (three rewrites the guards let through, sixteen answers that matched the deterministic text, eleven that matched the macOS expectation); it is a report, not a gate, because sampling differs and the guards decide what is inserted.

On the development machine (RTX 4090) the Vulkan build loads the 1.7B model and answers a rewrite in 650 ms through the supervisor, and the device's usage read from `status` goes from 6,971 MB before the load to 8,102 MB loaded and back to 6,933 MB once the reaper has unloaded the engine after a one-second idle (`docs/reports/llm-idle-unload-report.json`); the CPU build answers the same rewrite in 0.6 s after a 0.8 s load. The Vulkan build compiles llama.cpp's shaders with the system `glslc` and needs the Vulkan and SPIR-V headers; a machine without the system packages can point `CMAKE_PREFIX_PATH` at an unpacked Vulkan-Headers and SPIRV-Headers install.

Bounds: the engine serves one request at a time (two rewrites queue); a prompt longer than the context is `bad_request`; the memory figure under Vulkan is the whole device's usage as ggml's memory-budget query reports it, so the drop after `unload` is the number to read, not the absolute value; the CPU device reports no memory on this build, so `memory_bytes` is absent there. Meeting analysis prompts, fine-tuned models and an evaluation harness stay with their own specs.
