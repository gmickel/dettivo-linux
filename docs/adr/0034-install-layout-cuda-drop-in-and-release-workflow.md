# 0034: One install layout, a reserved CUDA drop-in, two AUR recipes and a self-publishing tag

Status: Accepted 2026-09-05; the CI cadence is superseded by [ADR 0040](0040-fast-ci-loop-proves-the-receipt-the-rig-runs-nightly-and-at-release.md): the package, both recipes and the clean-container install run in the nightly rig and at release, not on every push; amended 2026-09-06 by [0051](0051-the-release-gate-passes-on-validated-evidence-bound-to-the-tested-binaries.md) (a tag publishes only with the gate's receipt checked in for the gated code), by 0053 (both packages depend on qt6-multimedia), and by 0049 (the install test resolves --models to an absolute path), and by [0064](0064-a-release-publishes-itself-to-the-aur-and-the-plugin-mirror.md) (the release publishes both AUR recipes itself), and by [0065](0065-dettivo-for-linux-is-gpl-3-or-later.md) (the licence is GPL-3.0-or-later); what the tag runs is amended by [0070](0070-a-release-is-local-qa-and-a-tag.md)

## What this gives you

`yay -S dettivo-bin` puts the whole product on an Omarchy machine in one command: the daemon, the engines, the command line, the app, the pill, the QML module, the units, the desktop entry, the icons, the shell completions and the notice, each at the path the desktop already looks in. Nothing needs a hand step afterwards beyond enabling the socket in your session, and nothing needs a GPU: the three ggml engines carry the Vulkan backend and fall back to the CPU on their own. A release is a tag: `v0.1.0` becomes a GitHub release with the tarball, its checksums and the notes from the changelog after the same gate CI runs on every push, plus an install of the built package on a clean container (the package and install jobs have since moved to the nightly rig and the release run, ADR 0040). A later CUDA build of the engines drops into a directory the daemon already searches first, so it needs no daemon change and no second copy of anything else.

## The situation

The tree `scripts/package.sh` staged before this record had the binaries and the units, but no completions, icons or notice, and the Qt binaries it installed could not start: they linked `libDettivoStyle.so` with a runtime path that named only the `Dettivo` module directory. The engines were built for the CPU. There was no recipe an AUR helper could run, no release automation, and no test that installed the result anywhere but the development machine, so a packaging break would have surfaced on a user's machine. ADR 0013 had already decided on AUR packages with the engines as separate files; this record fixes the layout, the recipes and the release path that decision left open.

## The decision

The package installs one layout under `/usr` and `packaging/manifest.txt` lists every file in it. Binaries go to `/usr/bin` (`dettivod`, `dettivo`, `dettivo-mcp`, `dettivo-qa`, `dettivo-app`, `dettivo-osd`, `dettivo-sheet`, `dettivo-insert-target`, `dettivo-bar`). The engines go to `/usr/lib/dettivo/engines/dettivo-engine-{whisper,parakeet,llm,diarize}`, built with `--features vulkan` and falling back to the CPU at run time with the reason in `speech.engines`. The QML module goes to `/usr/lib/dettivo/qml/Dettivo` and `DettivoStyle` with their `qmldir`, and every Qt binary carries both directories as its runtime path while the style library carries the first, so the module resolves without `QML_IMPORT_PATH` or `LD_LIBRARY_PATH`. The Omarchy plugin folder goes to `/usr/share/dettivo/omarchy`. The units go to `/usr/lib/systemd/user` with a preset that enables `dettivod.socket` and `dettivo-osd.service` for new sessions. The desktop entry, the scalable mark and its 16, 32, 64 and 128 px renders, the completions `dettivo completions <shell>` generates for bash, zsh and fish, the licence and `NOTICE.md` go where the desktop, the shells and pacman look for them. Models never ship; `check-manifest.sh` refuses a tree with `usr/share/dettivo/models`.

The daemon searches for an engine in `[engines] directory` when set, then `/usr/lib/dettivo/engines-cuda`, then `/usr/lib/dettivo/engines`, then beside its own binary, then `PATH`, and `speech.engines` reports the directory that answered. The CUDA directory is reserved for a later `dettivo-engines-cuda` package: a file there wins over the default engine of the same name, and removing the package restores the Vulkan build without any other change.

Two AUR recipes under `packaging/aur/` install the same tree. `dettivo-bin` takes the release tarball and its `SHA256SUMS` from the GitHub release, verifies one against the other in `prepare()` and copies `usr/` into the package. `dettivo` takes the tagged source archive and runs `just package` inside `build()`, so the AUR build is the release build. Both carry the same runtime dependencies (Qt 6 base, declarative, svg and wayland, layer-shell-qt, tomlplusplus, wayland, libxkbcommon, PipeWire, the Vulkan loader) and the same install script, `.SRCINFO` is regenerated from `makepkg --printsrcinfo` and checked in step by `scripts/packaging/lint.sh`, and `packaging/aur/publish.sh` pushes both to the AUR by hand after a release exists; CI never touches the AUR.

The release workflow runs on a `v*` tag and on a manual dispatch whose `dry_run` input defaults to true. It first checks that the tag equals `Cargo.toml`'s version and that `CHANGELOG.md` has the version's section, then runs `just build test lint` and `just package package-bin` in the pinned Arch container, installs the built package on a second clean container through `scripts/packaging/install-test.sh`, and publishes the tarball, `SHA256SUMS` and the notes with `gh release create` before downloading them again and checking the sums. A dry run does everything but publish and leaves the three files as workflow artifacts. `ci.yml` ran the tree, both recipes and the install test on every push when this record was written; ADR 0040 moved them to `rig.yml`, nightly and at release, so a packaging break is caught by the rig before a tag.

The install test is one script with one report. `scripts/packaging/install-test.sh` installs the package with `pacman -U` on a clean root (or unpacks it under a prefix on a development machine), compares the file list with the manifest, validates the desktop entry and the units, checks `dettivo --version`, loads the three completion scripts in their shells, renders Home from the installed module on the offscreen platform, runs every engine's help, runs the CPU-fallback smoke through the three engines' command line modes under `DETTIVO_FORCE_CPU=1` and dictates the fixture through the installed daemon with the mock microphone, reading the completion event's timing against NFR-2. `--session`, on a fresh virtual machine, also enables the socket, proves activation under 300 ms, runs `dettivo setup` and starts the pill's unit. `install-test.json` names every step with its outcome, detail and exit code, and `dettivo-qa pack release` reads it as the packaging step beside the dictation pack and the strict contract replay.

## Release layout repair, 2026-09-14

Both AUR packages install the native QML modules under `/usr/lib/dettivo/qml`. CMake uses that private library directory for installation, host imports and runtime linking; the static Omarchy plugin stays under `/usr/share/dettivo/omarchy`. The common tree includes the MIT license at both `/usr/share/licenses/dettivo/LICENSE` and `/usr/share/licenses/dettivo-bin/LICENSE`, so either package identity satisfies Arch's license check with the same strict manifest.

The install recipe selects the application archive matching the recipe's exact version and package release. Debug-symbol and older-version archives may coexist beside it. The install runner rejects multiple package arguments and debug packages. Package builds require namcap to execute successfully and report no errors; warnings remain visible and advisory. On Arch, its wrapper runs with system Python so a project Python cannot hide the checker behind an import failure.

## Consequences

An engine binary is found by directory order rather than by a config key alone, so `[engines] directory` stays the one override and a CUDA package needs no configuration. The Vulkan build is the only build that ships; `DETTIVO_PACKAGE_CPU_ONLY=1` exists for a machine without the Vulkan headers and is never used for a release. The install test needs the test models (tiny.en, Parakeet TDT 0.6B v2 and Qwen3 1.7B) and downloads them into the CI cache; without a model an engine's smoke skips naming the fetch script. The source recipe builds parakeet.cpp from pinned archives fetched during `makepkg`, so it needs the network, which the AUR expects of source packages that vendor nothing. The manifest is a hand-maintained list: a new installed file fails the packaging step until it is added, which is the point. AppImage, Flatpak, Snap and the CUDA package itself stay outside this record, per ADR 0013.
