# 0080. whisper.cpp carries a DTW median-filter guard, and one bad chunk no longer fails a transcript

Status: Accepted 2026-09-29, amends [0074](0074-whisper-times-every-word-by-dtw-for-speaker-labelling.md). Amended 2026-09-30: an engine on the CPU after a GPU failure tries the GPU again after a hold of 2 minutes, doubling to at most 30, and a crash warning keeps the C++ runtime's Vulkan and ggml exception lines.

## What this gives you

A meeting, an import or a re-run finishes its transcript even when a stretch of the audio trips the speech engine. A clip whose last decoding window lasted between about 0.10 and 0.14 seconds used to abort the Whisper engine; the patched engine transcribes it. If the engine still dies twice on the same stretch, that stretch becomes one line, "[Not transcribed: speech recognition failed on this part]", at its place in the transcript, and the rest of the meeting is kept. An engine that crashes on the GPU, for instance while a game holds the GPU's memory, carries on on the CPU, and goes back to the GPU within a few minutes of the memory coming free. Every engine crash now logs the engine's last stderr lines, including the Vulkan error that made it abort. On a long meeting the speaker pass now runs its voiceprint and voice check, which silently stayed idle before, and the meeting analysis completes on the CPU when a game leaves the language model no room on the GPU.

## Situation

On 2026-09-29 a 57-minute two-track meeting failed its transcript at chunk 193 of 262 with `engine crashed`, twice, and was left `failed` with no transcript. The audio was intact.

The core dump, symbolized against a build with line tables, stopped in `median_filter` inside `whisper_exp_compute_token_level_timestamps_dtw`. [ADR 0074](0074-whisper-times-every-word-by-dtw-for-speaker-labelling.md) turned on whisper.cpp's DTW word timing in 0.4.0. That code asserts that a decoding window holds more audio tokens than the median filter is wide (seven), and a window of 0.10 to 0.14 seconds holds fewer. The assertion aborts the process through whisper.cpp's log, which the engine does not print, so the crash left no message. It depends only on the audio, so the retry crashed on the same chunk. About 0.12 seconds of the JFK fixture reproduces it on the CPU and on Vulkan, and upstream `master` still carries the assertion. `whisper-rs-sys` builds whisper.cpp only from the copy it ships, with no way to substitute a source.

The same investigation found three smaller gaps. The transcription job retried a crashed chunk once and then failed the whole transcript. The supervisor moved a Whisper engine to the CPU only when its GPU load failed, not when it died mid-request, which is what ggml does when a game takes the GPU's memory. And re-running the recovered meeting's speaker pass showed the voice embeddings of [ADR 0075](0075-two-track-meetings-use-both-tracks-to-name-speakers.md) and [ADR 0076](0076-each-sentence-is-checked-against-the-speakers-voices.md) failing on it: one `embed` reply for hundreds of spans exceeded the protocol's 1 MiB frame header, the engine could not send it and exited without a message, and the pass ran without the voiceprint and the voice check. The bench missed it because it embeds through the engine's CLI mode, which has no frame limit.

## Decision

- **Vendor and patch `whisper-rs-sys`.** `third_party/whisper-rs-sys` is the 0.15.0 release, without the ggml backends the workspace never builds, used through `[patch.crates-io]`. Its whisper.cpp returns from the DTW function before allocating anything when `n_frames/2 <= medfilt_width`, leaving that window's tokens with `t_dtw = -1`. Its README records the patch and how to move to a new release. `dettivo-engine-whisper`'s `dtw_short_window` test cuts short clips from the JFK fixture and runs them through the engine; without the patch it aborts with signal 6.
- **Time words without a DTW time from their segment.** In DTW timing, a word whose tokens have no DTW time takes its segment's span, kept in order and never past the next word.
- **Mark a chunk the engine cannot transcribe.** When a chunk's retry crashes too, the job gives the chunk one segment carrying `GAP_TEXT` as a single word, placed between the chunk's overlaps so the merger keeps it whole, and goes on. A job allows three such gaps; the fourth fails the job as before, because four chunks lost to crashes point at a broken engine. Other engine errors still fail the job. The live transcript already skipped a failed window and is unchanged.
- **Fall back to the CPU after a crash on the GPU.** When an engine loaded on a GPU with the `auto` backend crashes on a request, the supervisor marks that load for the CPU, as it already did for a failed Whisper load, so the retry and the requests after it run on the CPU. An explicit `vulkan` or `cuda` choice is never moved.
- **Try the GPU again after a hold (amended 2026-09-30).** The fallback holds for 2 minutes. The first request after that respawns the engine and loads it under `auto`, so it lands on the GPU when the GPU has room. When that attempt fails the same way (a GPU load that aborts, a crash on the GPU, or an `OutOfDeviceMemory` answer), the supervisor falls back again and doubles the hold, up to 30 minutes. A load failure answers the same request on the CPU. A request failure reaches its caller, which runs it once more on the CPU as the transcription job and the live transcript already do. The first request an engine serves on the GPU resets the hold to 2 minutes. An idle unload or a changed selection clears the fallback and its hold. The supervisor changes an engine's backend only as a request starts, so no request runs on the GPU and the CPU at once, and a retry costs at most the one CPU re-run above. The hold and the cap are constants in `dettivo-speech` (`Settings::gpu_retry_hold`, `GPU_RETRY_CAP`), with no configuration key. The supervisor has no way to measure free GPU memory, so each retry is a plain attempt.
- **Run the language model on the CPU when the GPU has no room.** A model loaded on the GPU under `auto` whose context or prompt fails before any text has streamed reloads on the CPU and runs the generation again. A model on the CPU keeps its context off the GPU (`offload_kqv` and `op_offload` off); llama.cpp would otherwise put the KV cache and large operations on the Vulkan device even with no layers there. `[meetings.analysis] timeout_ms` defaults to 30 minutes instead of 60 seconds: on the CPU the 57-minute meeting's analysis took 606 seconds, where on the GPU an hour's analysis takes about a minute.
- **Run Parakeet on the CPU when the GPU has no room.** parakeet.cpp answers a full GPU with an `inference: … ErrorOutOfDeviceMemory` error instead of aborting, so an engine that loaded while a game held most of the GPU failed every dictation and was kept warm. Under `auto` the engine now reloads the model on the CPU and runs the same request again; checked by starting it into a GPU with 1 GB free, where the first dictation failed on Vulkan, moved to the CPU and returned the transcript. The speech wrappers pass the backend a result reports to the supervisor, and the supervisor restarts an engine that answers GPU out of memory, marking its next load for the CPU, so no engine stays stuck on a full GPU.
- **Embed in batches.** The diarization client sends 128 spans per `embed` request, each with only the audio its spans cover, so a reply stays at a few hundred kilobytes whatever the meeting's length.
- **Log a crash's stderr, and a frame that cannot be sent.** The supervisor's crash warnings carry the redacted tail of the engine's stderr, and an engine logs an error before it stops over a frame it could not write. Redaction and the crash warning keep libstdc++'s two lines for an uncaught exception, matched by format (amended 2026-09-30). The line `terminate called after throwing an instance of '<type>'` stays when the type is a plain C++ name, and the `what():` line after it stays when its message starts with `vk::` or `ggml`, such as `vk::Device::allocateMemory: ErrorOutOfDeviceMemory`. A `what():` line with any other message is redacted like the rest of the stderr, so transcript text still never reaches the log. On 2026-09-30 the warning dropped both lines, and telling a full GPU from any other Vulkan failure took a core dump.

## Consequences

- The repository carries about 7 MB of third-party C, C++ and Rust under `third_party/`. The file-length lint allows `third_party/**`, the notice lint leaves path crates out of its crate table, and `NOTICE.md` names the vendored crate. Moving `whisper-rs` to a release that bundles a newer whisper.cpp means refreshing the copy and reapplying the patch, which the README spells out and the `dtw_short_window` test checks.
- The words of a window whisper.cpp could not align carry their segment's span, a coarser time than DTW gives. Such windows are at most 0.14 seconds of audio.
- A transcript can now complete with up to three marked gaps where it used to fail; the gap line shows in the app, in exports and in the analysis's input.
- After a GPU failure the engine runs on the CPU for at least 2 minutes, and for up to 30 minutes when the GPU stays full. On 2026-09-30 back-to-back meetings kept Whisper loaded, so under the first rule it stayed on the CPU for more than two hours with the GPU mostly free, and each meeting took about as long to transcribe as it had lasted. A full GPU now costs a failed attempt at most every 30 minutes, and each such attempt runs its request again on the CPU. The language model engine's own fallback cannot be exercised in CI, which has no GPU; it was checked on the development machine with a game holding the GPU.
- A provider that hangs now shows the analysis running for up to 30 minutes before it fails; `meetings.analyze` cancels and runs it again at any time.
