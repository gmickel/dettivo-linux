# 0035. Diarization runs sherpa-onnx in its own engine process after the meeting, and a segment gets a speaker only under the coverage and share rule

Status: Accepted 2026-09-05, corrected 2026-09-06 by 0053 (the speakers migration is 0006-speakers), amended 2026-09-09 by [0057](0057-cuda-diarization-drop-in-with-cpu-fallback.md) (optional CUDA provider and paired release pins) and [0058](0058-strict-diarization-accuracy-evaluation.md) (calibrated model, clustering and accuracy evaluation)

## What this gives you

A finished meeting says who spoke. Once the finalisation lands, the daemon runs the system track (the whole microphone track of a room-audio meeting) through `dettivo-engine-diarize`, labels your own segments `You` and each remote segment with the speaker whose turns cover it, keeps the speakers with their talk time on the row, and shows the pass as `job.progress` chunks and a `diarization_status` on `meeting.state`. `dettivo meetings diarize <id>` runs it again with a speaker count, `dettivo meetings speakers rename <id> speaker_00 Ada` names a speaker across the transcript, the exports and the search index, and the name is offered for the next meeting. The model set is one catalogue download of 47 MB, and the pass runs at about sixteen times real time on four CPU threads, so the labels arrive a few seconds after the transcript.

## Situation

ADR 0004 fixed Sherpa-ONNX as the one non-ggml family, for diarization alone, because no ggml diarization exists and the pyannote segmentation 3.0 plus 3D-Speaker ERes2Net pair had proved itself on Windows at a small size. ADR 0003 gave every inference its own supervised process, ADR 0031 put both sides of a meeting on one clock as `you` and `remote` segments, and the meeting row already had a `speaker` slot the contract reserves. Four things had to be decided: how sherpa-onnx is bound, since its C++ core links ONNX Runtime and nothing else in the workspace may; how a pass that ONNX Runtime cannot interrupt answers a cancel; how a two-file model set travels through a catalogue built for one file per model; and which rule turns speaker turns into labels on segments the engine cut for other reasons.

The `sherpa-rs` crate was the candidate binding. Its static route needs `-C relocation-model=dynamic-no-pic` on every crate in the workspace, which would strip position independence from the daemon; its default route downloads the prebuilt shared libraries and copies them into the target directory by walking up from `OUT_DIR`, and pulls the text-to-speech surface in by default. The release archive it fetches is the same one an in-repo binding can fetch, checksummed, the way `parakeet-cpp-sys` fetches parakeet.cpp (ADR 0018).

## Decision

- **An in-repo binding over the release archive.** `crates/sherpa-onnx-sys` fetches `sherpa-onnx-v1.12.9-linux-x64-shared.tar.bz2` from the k2-fsa release (SHA-256 pinned in `build.rs`; `SHERPA_ONNX_ARCHIVE_DIR` and `SHERPA_ONNX_DIST_DIR` point at a copy already on disk), keeps `libsherpa-onnx-c-api.so` and the `libonnxruntime.so` it carries with an `$ORIGIN` run path under its `OUT_DIR/lib`, links the C API dynamically, exports the directory as `DEP_SHERPA_ONNX_LIB_DIR`, and binds the offline speaker diarization surface of `c-api.h` with bindgen. `dettivo-engine-diarize` is the only crate that links it and sets its own run path to `$ORIGIN`, `$ORIGIN/../lib/dettivo` and that directory, so a packaged install ships the two libraries beside the binary or under `lib/dettivo` and a build tree needs nothing copied. ONNX Runtime is loaded into that one process and never into the daemon or a ggml engine.
- **The fourth engine.** `dettivo-engine-diarize` speaks the engine protocol through `dettivo-engine-proto::host_diarize`, a host that keeps reading frames while a pass runs on its own thread: `load` names the model directory (`segmentation.onnx`, `embedding.onnx`) and, new to the protocol, `threads` (0 is the core count capped at four); `diarize` takes the `pcm16k` attachment with `speakers` as the cluster count when known and `clustering_threshold` otherwise, streams `progress` events with `completed` and `total` beside the fraction (the pipeline's own embedding chunks, at most ten a second), and answers `turns` labelled `SPEAKER_00`, `SPEAKER_01`, ... in start order; `status` says `busy` meanwhile; `loaded` reports `cpu` with the reason, and `DETTIVO_FORCE_CPU` changes nothing. sherpa-onnx's progress callback cannot stop the pass, so a `cancel` for the running request is answered at once with `cancelled`, the pass finishes in the background and its result is dropped, and any request that arrived meanwhile is answered afterwards in order. The CLI mode `--wav <file> --model <dir> --json [--speakers n] [--threshold t] [--threads n]` prints the same JSON. The daemon's `DiarizeEngine` (`dettivo-speech::diarize`) drives it over the supervisor with the speech engines' slot mechanics (`stt_idle_seconds`, backoff, degraded after three crashes in a row without a good load between them) and a cancel flag the supervisor's new `call_cancellable` turns into a `cancel` frame mid-request.
- **A model set in the catalogue.** A catalogue entry may carry `files` beside its own file and an `unpack` step (`tar.bz2`, the member, its checksum and size): `diarize/diarization` is the pyannote archive unpacked to `segmentation.onnx` (MIT) and the 3D-Speaker ERes2Net file as `embedding.onnx` (Apache-2.0), 47 MB in all. The downloader fetches the files one after the other under one progress, verifies each download against its checksum and an unpacked member against its own, skips a file already on disk and verified, and lands the set with one manifest; readiness is `ready` when every file is present and verified, `partial` with the bytes on disk while some are, and one corrupt file quarantines the set. `speech.models.status|download|cancel|delete` accept `provider = "diarize"` while `speech.providers.list` and the selection methods keep listing the speech providers alone, as they hide the language models. The engine loads the directory.
- **The pass and the rule.** When a finalisation or a meeting import lands `completed` and `[meetings.diarization] auto` applies (the meeting's own `diarize` first), or when `meetings.diarize` asks, the daemon reads every take of the diarized track onto the meeting clock with the gaps as silence and sends it in one request. The engine's labels are renumbered in order of first appearance (`speaker_00` is whoever spoke first) so a re-run maps onto the same ids. For a remote segment, coverage is the share of its span inside any turn and the winner is the speaker with the most overlap; the label is assigned only when coverage is at least `min_coverage` (0.25) and the winner holds at least `min_speaker_share` (0.60) of the segment's diarized speech, so a segment straddling two turns evenly and a silence-heavy one stay unlabelled. Microphone segments are `You` (`you`); in a room-audio meeting every segment is assigned from the turns. The speakers land on the row with `talk_ms` summed over their segments and a swatch index in order of first appearance (`you` first), the diarization block records `status`, `coverage`, `engine`, `model`, `ran_at` and `error`, and a re-run keeps the names by id when the diarized count matches, else the row's speakers are rebuilt and the names live on as suggestions.
- **Names.** `meetings.speakers.rename` (at most 64 characters; empty restores `You` or `Speaker N`) updates the speaker row and the `speaker` text of every segment, so `txt`, `md`, `srt` and `vtt` carry the name and `json` carries the speakers; migration `0006-speakers` keeps the speakers in `meeting_speakers`, joins the names to the meetings FTS index so `meetings.search` finds a meeting by who spoke, and remembers every given name in `speaker_names` for `meetings.speakers.suggest`, most recent first.
- **Surfaces.** `meetings.diarize`, `meetings.speakers.list|rename|suggest`, `expected_speakers` and `diarize` on `meetings.start` and the meeting import, `speakers` and `diarization` on `meetings.get`, `speaker_count` on `meetings.list`, `speaker_id` and `speaker_confidence` on every segment, `diarization_status` on `meeting.state` and the `diarizing` stage on `job.progress` are registered in `docs/api/linux-deltas.md` with fixtures. The configuration is `[meetings.diarization]` (`enabled`, `auto`, `model`, `min_coverage`, `min_speaker_share`, `max_speakers`, `clustering_threshold`) and `[engines.diarize] threads`.

## Consequences

- The evidence: `crates/dettivo-qa/fixtures/diarization/two-speakers.wav` is two Piper voices (`en_US-amy-low`, `en_US-ryan-low`, synthesised through sherpa-onnx's own offline TTS by `scripts/qa/make-diarization-fixture.py`) taking six turns with one overlap, with the expected turns beside it; `dettivo-qa pipeline diarization` scores the engine's CLI mode by diarization error rate under the best speaker mapping and passes under 0.20 with exactly two speakers, recording 0.020 (missed 0.011, false alarm 0.009, no confusion) and 16.5 times real time with `--bench` on four threads of the development machine, which meets NFR-4's four times. `crates/dettivod/tests/meetings_diarize.rs` runs the two-track meeting, the room-audio import, the re-run, the refusals and the rename against the live daemon, and `meetings_diarize_crash.rs` injects the supervisor's crash markers into the scripted engine: the pass fails with the engine's last redacted line, the daemon keeps answering, the meeting stays `completed`, the third crash in a row degrades the engine, and a re-run after the backoff lands `ready`. CI fetches the model set with `scripts/models/fetch-diarization-model.sh` and runs the fixture tests and the pipeline on the CPU.
- Bounds: CPU stays the default package; [0057](0057-cuda-diarization-drop-in-with-cpu-fallback.md) adds an optional CUDA drop-in with automatic CPU fallback and supersedes the CPU-only provider and 1.12.9 release-pin decisions above; a cancel answers at once but the engine stays busy until sherpa-onnx returns, and the supervisor's idle reaper or terminate ends a process that is no longer wanted; one speaker on the remote track labels every covered segment `Speaker 1`; the segment boundaries are the transcription engine's, so a segment that spans a speaker change is left unlabelled rather than split. The clustering decides the count unless `expected_speakers`, `speakers` on a re-run or `[meetings.diarization] max_speakers` fixes it. A meeting deleted while the pass runs has its result dropped when the pass ends; a running pass is cancelled through `meetings.cancel` on the completed meeting.
- The speaker popover, the talk-time bar and the swatches in the app, meeting notes and analysis are their own specs; `color_index` is the swatch slot they read.
