## Native desktop limitation

Native attempts used the existing Hyprland desktop, its XWayland display `:0`, and private seeded QA profiles. They did not establish a native R4 pass.

| Attempt | Observation | Evidence root |
|---|---|---|
| Stock AT-SPI run | No focused control; all seven Home Tab controls unreached | `/tmp/dettivo-fn38-native-atspi/` |
| Owned-window X11 activation | `xdotool` reported missing `_NET_ACTIVE_WINDOW`; no focused Home control followed | `/tmp/dettivo-fn38-native-activated/` |
| Immediate Hyprland focus request | The window had not yet appeared in the compositor's client list | `/tmp/dettivo-fn38-native-hypr-focus/` |
| Focus request after compositor discovery | The owned XWayland client was observed and `hl.dsp.focus` returned `ok`, but the active PID remained different; the keyboard run failed | `/tmp/dettivo-fn38-native-compositor-ready/` |
| CUA with foreground delivery | The first Tab failed with `press_key: unreadable answer: expected ident at line 1 column 2` | `/tmp/dettivo-fn38-native-cua/` |

The last two attempts retain the owned PID and compositor observation in `activation.json`. The repeatable coordinator is `/tmp/dettivo-fn38-native-driver.py`; it selects only direct child QA app processes. The [documented Hyprland dispatcher](https://wiki.hypr.land/Configuring/Basics/Dispatchers/#window) supplied the exact PID selector. These observations establish a missing native automation proof, not a diagnosis of an application keyboard defect. No desktop configuration or installed driver was changed.

CUA's separate Xvfb probes tried `press_key` and `hotkey`, targeted the owned window and verified the US slash/question keymap. The tool reported an unverifiable effect while the sheet remained closed. The complete supplement is `/tmp/fn38-finaldate-beauty/keyboard-evidence.md`.
