# History

Every dictation you finish is kept and findable, and an hour of audio in any of the contract's formats becomes an item just like it. The daemon writes each dictation into a SQLite database the moment the insertion is done, with the text before and after the mode step, where it went, which engine and model produced it, which Polish policy it ran under, how long the take was, and the take itself when audio is retained; an import adds the segments with their timestamps and, from an engine that aligns words, the words. From there you can list, read, search, re-insert, re-run with another model, export and import it, from the command line, from any client of the contract, and later from the app.

```
dettivo history list [--limit N] [--app <app id>] [--since <date>]
dettivo history get <id> [--words]
dettivo history latest
dettivo history search <words> [--limit N]
dettivo history delete <id>
dettivo history rerun <id> [--model M] [--provider P] [--mode raw] [--no-wait]   # raw only for now
dettivo history cancel <id>
dettivo history export [--scope item|range|all] [--format json|markdown|txt|zip] --out <file> [--id <id>] [--from <t>] [--to <t>]
dettivo history import <file.wav|.mp3|.m4a|.aac|.caf|.aiff|.flac|.ogg|.zip> [--language en] [--provider P] [--model M] [--no-wait]
dettivo dictation reinsert-last
```

`latest` prints the id and the text of the newest item; `list` prints one row per item (id, start time, seconds, status, title); `get --words` prints every segment as `[mm:ss.mmm - mm:ss.mmm] text` with the words indented under it when the engine aligned them; `--json` prints the daemon's result for a script. `dettivo doctor` reports the database path, size, item count and the last migration on its `history` row.

## The store

The database is `$XDG_DATA_HOME/dettivo/dettivo.db` (`[history] db_path` moves it), opened in WAL mode with foreign keys on and a five second busy timeout, so a backup tool or a second reader never blocks the daemon for long and a method that still hits a held lock answers `INTERNAL_ERROR` with `reason = database_busy` and can be retried. One table, `dictations`, carries the macOS `DictationItem` fields: id, created and updated times, app id and name, source kind (`dictation`, `audioImport`, `rerun`), status (`transcribing`, `completed`, `failed`), mode, provider, model, language, raw and final text, title, summary, duration, the item a re-run came from, an error code and message, the retained audio path and the insertion result as it was reported, plus (migration `0002-segments`) the segments with words an import or re-run produced and the notice an empty transcript carries (`silent`), and (migration `0003-polish-policy`) the hash of the Polish policy the session ran under; the same notice column carries, when the Enhanced pass inserted the deterministic result, the reason why ([docs/polish.md](polish.md)). Rows written before those migrations have none of them. A cancelled job leaves its item `failed` with `error_code = cancelled`, which `transcripts.list` reports as `cancelled`.

Migrations are numbered SQL files inside the daemon. Before the first pending one runs against a database that already has content, the daemon writes a consistent copy next to it (`dettivo.db.bak-<version>`); a migration that fails stops the daemon at start with the migration's name and that backup path on standard error, and nothing else has been touched. Migration `0004-meetings` adds the `meetings` table with the macOS `MeetingSession` fields (title and its source, status, start and end, duration, language, provider and model, `is_partial` with the chunk counts, the disclosure time, the capture facts, the texts and segments, the errors) and its own FTS5 index; `transcripts.list` with both kinds walks one timeline over the two tables, newest first, with a `created_at|kind|seq` cursor ([docs/meetings.md](meetings.md)). Migration `0006-speakers` adds the speaker rows, the remembered names and the speaker names to the meeting index (ADR 0035); migration `0007-notes-analysis` adds the notes and analysis columns and rebuilds the meeting index over title, transcript, speaker names, notes and analysis (ADR 0036); migration `0008-analysis-queued` widens `analysis_status` to admit `queued`, the plan the finalisation writes before it announces `completed` (ADR 0061). Meeting audio lives under `$XDG_DATA_HOME/dettivo/meetings/<id>/` and is kept until the meeting is deleted; the `[history]` sweep never touches it.

Retained audio lives beside the database: `$XDG_DATA_HOME/dettivo/dictations/<id>/microphone.wav` (16 kHz mono; several takes of one session are joined into one file) with `metadata.json` holding the item's fields. A dictation is stored before its final `dictation.state` is published, so a client that sees `idle` can read the item back at once. When the store cannot take the item (a locked database, a full disk), the insertion still happened: the final state carries `reason = history: <why>`, the session keeps the transcript for `reinsert-last`, and the journal names the cause. This recovery is the existing one-slot in-memory last transcript; it does not survive daemon exit and can be replaced by a later completed session. Sessions write no second transcript archive. Staging is discarded after archival, and cancelled sessions discard their takes regardless of `keep_audio`.

## Retention

`[history]` in `config.toml` decides what is kept ([docs/config.md](config.md)):

| Key | Default | Effect |
|---|---|---|
| `keep_audio` | `true` | The take of every finished dictation moves into the item directory. Off, the take is discarded and the item has no audio to re-run. |
| `audio_retention_days` | `30` | An hourly sweep removes retained audio older than this; `0` keeps it. |
| `max_items` | `0` | The sweep removes the oldest items beyond this count; `0` keeps every item. |
| `artifacts` | `"keep"` | What lives beside the database and what a delete removes: `keep` writes audio and `metadata.json` and a delete removes the item directory; `audio_only` writes the audio alone and a delete removes it; `none` writes nothing beside the row and a delete removes the row. |
| `db_path` | `""` | The database file; empty means `<data_dir>/dettivo.db`. |

The sweep runs at start and then every hour; it skips any item a re-run or import job is using. `dettivo history delete <id>` removes the row and its artifacts per the policy at once, and answers `CONFLICT` while a job uses the item.

## Search

`dettivo history search <words>` and `transcripts.search` run SQLite FTS5 over the raw text, the final text, the title and the summary, of dictations and meetings alike (`meetings.search` is the meeting half alone). Every word you type matches the start of a word in any of those fields, all words must match, and accents are folded, so `cafe` finds `café` and `api gate` finds the API gateway note. Quotes, parentheses and operator words are search terms, never syntax. A query over 1024 bytes, or one with no word characters at all, is `INVALID_PARAMS` naming the limit. Hits carry a snippet around the match and `score = null`: ranking is FTS5's, and `system.capabilities.history` reports `fts = true`, `semantic_search = false` until the knowledge spec adds embeddings.

Listing is keyset-paged: `transcripts.list` takes the `cursor` it returned for the next page, and the Linux additions `app_id`, `since` and `until` narrow it (`--app`, `--since` on the command line).

## Re-run

`dettivo history rerun <id> --model tiny.en` transcribes the item's retained audio again with the model (and optionally provider or mode) you name and stores the result as a new item with `source_kind = rerun` linked to the original through `rerun_of_item_id`. The new item appears at once with status `transcribing`, the job runs through the same chunked pipeline as an import (below) and reports through `job.progress`, and the item ends `completed` with its text and segments or `failed` with the engine's reason; the command waits and prints the text unless `--no-wait`. An item without retained audio answers `NOT_FOUND` with `reason = audio_not_retained`; a model that is not on disk names itself and the `dettivo speech download` command to run; a mode other than `raw` answers `NOT_IMPLEMENTED` naming the layer a rerun runs, because a rerun and an import stay on the raw layer (ADR 0023). `dettivo history cancel <id>` (`transcripts.cancel`) stops the job on an item between two chunks.

## Export and import

CLI file transfers read, write and hash bounded chunks. Exports publish a sibling temporary file only after the daemon acknowledges completion, preserving an existing destination on failure.

Exports and imports move through the contract's chunked transfers ([docs/api/dettivo-ipc-v1.md](api/dettivo-ipc-v1.md) section 8.9), and the command line drives them for you.

- **Export**: `transfer.begin { direction: download }`, then `transcripts.export` with the transfer id, the format and, as Linux additions, a `scope` (`item`, the contract's one-item export; `range` with `from` and `to`; `all`) and the format `zip`, which bundles `items.json` with every item's audio. The daemon renders into `$XDG_CACHE_HOME/dettivo/exports/` and `transfer.pull` streams it back chunk by chunk. `json` carries every field, `markdown` one section per item with its facts, `txt` a timestamp line and the text per item; an empty range is an empty document, not an error. A meeting reference exports one meeting as `txt`, `md`, `json`, `srt` or `vtt` (`meeting.<format>`), the contract's meeting formats.
- **Import**: `transfer.begin { direction: upload, content_type }` with one of `audio/wav`, `audio/mpeg`, `audio/mp4`, `audio/m4a`, `audio/aac`, `audio/x-caf`, `audio/caf`, `audio/aiff`, `audio/flac`, `audio/ogg` or `application/zip` (any other type is `INVALID_PARAMS` listing these), `transfer.chunk` in order from 1 (a chunk more than `max_inflight` ahead is `RATE_LIMITED_LOCAL`; an upload past `[transfer] max_upload_bytes`, 1 GiB, is `INVALID_PARAMS` naming the limit), `transfer.commit` with the chunk count and the SHA-256 of the whole file, then `transcripts.import { transfer_id, target_kind, filename, language, mode, provider?, model? }`. An audio file becomes an `audioImport` item and a job (the next section), or with `target_kind = meeting` an imported meeting after the disclosure gate ([docs/meetings.md](meetings.md)); a Dettivo archive restores every item it holds that the profile does not have yet, with the same ids and audio, and answers at once. One import runs at a time: a second is `CONFLICT` with kind `importAlreadyInProgress`. Uploads spool under `$XDG_CACHE_HOME/dettivo/transfers/` and an idle transfer expires after `transfers.timeout_seconds`.

## Importing audio

`dettivo history import recording.m4a` gives you one item with the whole transcript, its segments on the recording's clock and a progress line per chunk while it runs, for a file of any length up to four hours in any of the formats above. The command line picks the content type from the extension (`.wav`, `.mp3`, `.mp4`, `.m4a`, `.aac`, `.caf`, `.aif`/`.aiff`, `.flac`, `.ogg`/`.oga`/`.opus`), pushes the file up in chunks, starts the import and follows `job.progress` on standard error (`job_import_1 decoding`, `job_import_1 transcribing chunk 2/3`, `job_import_1 merging`, `job_import_1 done`) until the item settles, then prints the id, the status and the text; `--no-wait` returns as soon as the job started, `--provider` and `--model` pick the engine for this import and default to `[speech]`, `--language` defaults to `en`. `dettivo history get <id> --words` shows what was stored.

The daemon does the work in its own thread, so the import call answers at once with the running job (ADR 0022):

1. **Probe.** The upload is opened with Symphonia as the type it declares. A container that is something else is refused naming both (`the upload declares audio/flac but its container is mp3`), and a file whose container reports a duration over `[history] max_import_seconds` (14400) is refused naming the limit before anything is decoded. A lossy file that reports no duration is measured while it decodes and refused at the limit then.
2. **Decode** (`stage = decoding`). Every format decodes in-process to 16 kHz mono, packet by packet, resampled through a windowed sinc; nothing shells out and a one-hour file never sits in memory whole. With `[history] keep_audio` on the decoded audio is the item's retained `microphone.wav`, ready for a re-run; off, it lives in a temporary file the job removes. Ogg carries Vorbis or FLAC; Opus has no decoder here and is refused naming the codec.
3. **Chunk and transcribe** (`stage = transcribing`, one event per chunk). The audio is cut into `[transcribe] chunk_seconds` windows (30) that overlap by `overlap_seconds` (2), each cut moved to the quietest 50 ms inside the window's last `safety_margin_seconds` (5) so a chunk rarely ends mid-word; a file shorter than one window is one chunk on the same path. Quiet edges are trimmed with 400 ms padding before each chunk reaches the engine. Automatic language detection runs independently on the remaining speech; an explicit language is retained. Segment and word times are shifted back to the original audio clock. A chunk whose level stays under `silence_rms_floor` (0.0065 RMS) in every 200 ms frame never reaches the engine and adds no text, so a silent hour ends as an empty transcript with `notice = silent` and never invented words; the known filler phrases Whisper writes into silence (`thanks for watching` and its kin, `filler_filter`) are dropped before the text is stored. An engine crash on a chunk is retried once; a second crash fails the item naming the chunk (`chunk 7 of 12 failed`) and keeps the text of the chunks before it. A provider without timestamps is refused naming the capability.
4. **Merge** (`stage = merging`). Consecutive chunks are reconciled inside their overlap: the later chunk's words win from the midpoint, a word the later chunk repeats within 250 ms of one the earlier chunk kept is dropped, a run of words at the seam the earlier chunk's tail already said inside the shared audio (within 1.5 s of it) is dropped once, and segment boundaries snap to the words that remain. Chunks that share no audio are not reconciled, so a word said again after a gap stays said twice. Whisper returns segments without word times, so its words are spread evenly over each segment for the merge and only the segments are stored; Parakeet's words with their timestamps and confidence are stored and `get --words` prints them.
5. **Store** (`stage = done`, progress 1.0). The item is `completed` with `text_raw`, `text_polish` (the raw pipeline applied), the segments, the duration of the decoded audio and the language the engine reported. `dettivo history cancel <id>` between two chunks leaves the item `cancelled` with the finished chunks' text and `stage = cancelled` on the last event; a failure ends with `stage = failed`.

`job.progress` carries `progress` (chunks done over chunks total), `chunks_done`, `chunks_total` and `stage` on every event of an import or re-run job, so a client shows `2/3` rather than a bare fraction. The pipeline's values live under `[transcribe]` in `config.toml` ([docs/config.md](config.md)) with a 30-second default window for language switching; `dettivo-qa pipeline import-merge` proves the chunker and the merger against a golden through the engine's own command line on every CI run ([docs/qa.md](qa.md)).

## The seed for drives

`DETTIVO_E2E_SEED=1` (with QA mode on) seeds twelve dictation items across three days and two apps at daemon start, the same rows every time, the newest being the contract's sample dictation, plus the contract's sample meeting (`Weekly sync`, thirty minutes, one segment); every dictation row carries the mock insertion backend and a stop-to-insert split, so the app's detail has its facts to show. With `keep_audio` on and `audio_retention_days = 0` the daemon also writes one second of silence as the take of row 11 (the design-call summary) and points the row at it, so the `history_seeded` drive can re-run an item while the contract sample keeps no audio for the `audio_not_retained` fixture; with any age limit the sweep would remove a take dated in February at once, so the seed writes none. The QA rig's contract replay starts its daemon with the seed so the `transcripts.*` and `meetings.*` fixtures have rows to answer with, and the export goldens under `crates/dettivo-storage/tests/goldens/` are the seed rendered in each format (the one row with a take differs from the golden in its `audio_path`, which the tests level).

## In the app

The app's History route lists, searches, opens, re-runs, exports and deletes these items through the same methods ([docs/app.md](app.md)); `transcripts.get` answers the detail's facts in one call, `transcripts.search` names where each hit's words start so the list can paint them, and the completion timings are stored with the item (migration `0005-timings`) so the stop-to-insert time outlives the pill ([ADR 0025](adr/0025-history-detail-facts-playback-and-export-file.md)).
